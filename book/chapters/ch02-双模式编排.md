# 第二章 · 双模式编排

## 本章能回答什么

- 为什么一个"调研助手"里会同时存在两条执行路径，而不是一条"更聪明的"。
- 这两条路各自的最坏情况是什么——**有界**这两个字具体由什么保证。
- 一次任务结束时，系统怎么把"为什么停"这件事说清楚（而不是只给一个成败）。

## 为什么不是一条路

确定性流水线（默认）与有界 ReAct（`AGENT_MODE=react`）解决的是两个不同的问题：

- **流水线**回答"同样的输入能不能得到同样的过程"。它的价值是**可复算**：
  任何一次产出，都能按步骤重放。
- **ReAct** 回答"能不能少抓一点页面"。它的价值是**成本**：靠推理挑页，
  而不是把站内页全捞一遍。

这两件事天然冲突：越依赖模型的自由发挥，越难复算。
所以做法不是"选一个更好的"，而是**两条路都留着，并且都能被同一套评测对照**
（第 6 章的 `react_compare` 就是干这个的）。

## 模式在哪里切换

模式是**运行时**读的，不是编译期分支：

```python
self._agent_mode = agent_mode      # None → 使用点运行时读 AGENT_MODE 环境变量
```

`research-agent@ef7204f src/workflow/mvp_workflow.py:572`

这一点很重要：如果模式是构造期固化的，那么"同一个任务用两种模式各跑一遍"
就需要两套代码路径；运行时读意味着**同一个进程里可以对照**，
这也是第 6 章能拿 ReAct 与流水线做同 case 对照的前提。

## "有界"由什么保证

ReAct 那侧不是"让模型自己决定什么时候停"。它有三道硬边界，全部写在循环里：

| 边界 | 实现位置 | 触发后 |
|---|---|---|
| 步数 | `research-agent@ef7204f src/agent/runner.py:74`（`for index in range(1, self.max_steps + 1)`） | 走预算收束 |
| token | `research-agent@ef7204f src/agent/runner.py:77` | `stop_reason = "budget_exceeded"` |
| 墙钟 | `research-agent@ef7204f src/agent/runner.py:80` | 同上（trace 里保留耗时） |
| 美元 | `research-agent@ef7204f src/llm/token_budget.py:152` | 同上 |

守卫放在**每轮开头**（`research-agent@ef7204f src/agent/runner.py:75`），
不是放在每轮结束——放在结束意味着"这一轮已经花掉了才停"，边界是软的。

步数默认 8，配置注释里写清了为什么不能更小：
≤3 会退化成"固定几步"，演示不出与流水线的区别
（`research-agent@ef7204f src/agent/config.py:7`、`research-agent@ef7204f src/agent/config.py:15`）。

## "为什么停"怎么说得清

一次任务结束时，系统不只给成败，而是给一个**终止原因**。它是落在 state 里的具体字符串，
不是异常里的一句日志：

| 原因 | 位置 |
|---|---|
| 抽取数据不足或缺来源 | `research-agent@ef7204f src/workflow/mvp_workflow.py:862` |
| 数据质量不足 | `research-agent@ef7204f src/workflow/mvp_workflow.py:888` |
| 所有步骤执行完成 | `research-agent@ef7204f src/workflow/mvp_workflow.py:1136` |
| 执行失败（带异常文本） | `research-agent@ef7204f src/workflow/mvp_workflow.py:1143` |
| ReAct 侧的具体停止原因（前缀 `react:`） | `research-agent@ef7204f src/workflow/mvp_workflow.py:1258`、`research-agent@ef7204f src/workflow/mvp_workflow.py:1279` |

把 ReAct 的停止原因**带前缀并入同一个字段**是刻意的：读者不需要知道内部有两条路径，
就能看出"这次是被预算截停的"还是"跑完了"。这条信息的价值在第三章会展开——
它决定了报告是 `completed` 还是 `partial`。

## 两条路怎么对照

对照指标叫 `react_compare`，核心量是**抓取削减率**（`fetch_reduction`）：
ReAct 相对流水线少抓了多少页面，同时要求引用指标不下降。

```python
"fetch_reduction": round(reduction, 3) if reduction is not None else None,
```

`research-agent@ef7204f evals/runner.py:420`（指标构造）、`research-agent@ef7204f evals/runner.py:394`（函数定义）

这一条是本卷对"架构装饰"的定义：一个 ReAct 实现如果削减不了抓取量，
它就只是给流水线套了个循环，**不值得为它付出不可复算的代价**。
第 6 章会给出这条对照 case 的判据。

## 可验证主张

| # | 主张 | 怎么判死 |
|---|---|---|
| 1 | 模式在运行时解析，不固化在构造期 | 读 `mvp_workflow.py:572` 的注释与赋值，并在启动时改 `AGENT_MODE` 观察行为 |
| 2 | ReAct 循环有**硬上界**，不是"模型说停才停" | `src/agent/runner.py:74` 的 `range(1, max_steps + 1)`；把 `AGENT_MAX_STEPS` 调小，步数随之减少 |
| 3 | 预算守卫在每轮**开头**检查 | `src/agent/runner.py:75-88`：先算 elapsed 与 token，再决定是否进入本轮 |
| 4 | 终止原因是落库字段而不是日志文本 | `mvp_workflow.py` 有 6 处赋值，落在 `state["termination_reason"]` |
| 5 | 两条路有可量化的对照，而不是各说各话 | `evals/runner.py:394`（`collect_react_compare`）与 `:420`（`fetch_reduction`） |
