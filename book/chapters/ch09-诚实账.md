# 第九章 · 诚实账

## 本章能回答什么

- 这套东西**哪些真的验过**，验到什么程度。
- 哪些**没验**，为什么没验，读者可以怎么自己补。
- 为什么"CI 全绿"不能直接当成结论——以及这一卷里出现过的三个具体反例。

`.github/workflows/ci.yml:51`（E2E 契约）、`.github/workflows/ci.yml:300`（离线评测门禁）、`.github/workflows/ci.yml:320`（Docker 构建）。

## 二、没验的（以及为什么）

**1. 真实 LLM 端到端。** `E2E real services` 需要模型与搜索密钥，
CI 上按设计 skipped（`research-agent@ef7204f .github/workflows/ci.yml:169`）。
这意味着：**所有"模型在真实环境里表现如何"的结论，这一卷都没验。**
本卷写的是"这条链路的结构与判据"，不是"它实际有多准"。这两件事不能混。

**2. 真实站点的抓取稳定性。** 评测走夹具，"站点结构变了怎么办"没有覆盖。
这是离线评测的固有代价，不是疏漏——但读者要知道它的边界在哪。

**3. 前端交互与导出。** 前端只入仓 34 个文件（`node:test` 有单独的作业），
PDF/文档导出路径这一卷没有逐一核过。

**4. `partial` 的报告"缺哪一节"。** 系统能告诉你"被预算截断了"，
但不会告诉你缺了什么。这是设计性挂起，不是 bug（见第三章）。

## 三、三个"CI 绿不代表结论成立"的反例

这一节是全卷的元讨论，也是这一卷存在的理由。

**反例一（第七章）**：CI 在一条只改了文档的提交上红，而真正原因是并发调度顺序。
**绿与红都可能与被改的那行代码无关**——所以"这次只改了文档，不会红"是错的直觉。

**反例二（第一章）**：README 长期写"14 条评测 case"，夹具实际 20 条。
文档落后于代码是常态，**数量类主张必须由测试钉住**，不能靠人工同步。
本卷写作期间已把 README 改成 20，并加了 `tests/test_readme_fixture_counts.py`
把"文档写的数 = 夹具实数"钉住。

**反例三（本章）**：上面那张"验过的"表里的每个结论，都依赖某个**前提**——
"705 passed"依赖 `pytest` 用的是项目 venv、"20 条全过"依赖夹具摘要校验通过。
前提变了，结论要重新核。这就是为什么本卷每条主张都带坐标而不是带结论。

## 四、怎么自己复核（照抄即可）

```bash
# 1. 环境（注意：不要用 PYTHONPATH=src 跑测试，见下面第五节的坑）
uv sync --extra dev

# 2. 全量测试
uv run --extra dev pytest -q

# 3. 离线评测门禁
uv run --extra dev python -m evals.runner --gate

# 4. 书里的坐标
python book/tools/audit_coords.py --print
```

## 五、两个"环境陷阱"，读者一定会踩

**1. `src/logging/` 会遮住标准库的 `logging`。**

`research-agent@ef7204f src/logging/__init__.py:1`

如果你用 `PYTHONPATH=src python -m pytest` 跑测试，会得到一个很像"代码坏了"的报错：
`AttributeError: partially initialized module 'logging' ... has no attribute 'getLogger'`。
真相是 `src` 被加进 `sys.path` 后，`import logging` 解析到了本仓的同名包。
正确跑法是 `uv run`（或用项目 venv），让包以 `src.logging` 的身份被导入。

**2. 可选依赖缺失时，MCP 只是降级，不是崩溃。**

`research-agent@ef7204f server.py:1565-1566`
`/mcp` 会回 503 并给出补救说明；主链路照常。看到 503 先查 `mcp` 包，不要以为服务坏了。

## 六、这一卷没写什么

- 没写"准确率/满意度"这类本仓没有真值的指标。
- 没写真实模型效果——那需要另一套带外部真值的评测，本卷只交代边界。
- 没把"设计意图"当成"已验证事实"：凡是注释里的话，正文都标明它是注释。
