# 《AI 产品工程卷》· 竞品调研 Agent 的可信性

> 本卷讲 `research-agent`：一个把「调研」做成可交付报告的产品，以及它**凭什么可信**。
> 全书 9 章，每一条事实性主张都挂坐标 `research-agent@ef7204f 路径:行号`。

## 怎么核这本书（三条命令）

```bash
# 1. 拿到书里引用的那个提交（锚点）
git checkout ef7204f

# 2. 随便挑一条坐标，看那一行是不是书上说的那一行
git show ef7204f:src/agent/citations.py | sed -n '168p'

# 3. 让门禁把全书的坐标都核一遍（少数没挂坐标的句子会在输出里点名）
python book/tools/audit_coords.py
```

## 门禁

| 工具 | 管什么 |
|---|---|
| `book/tools/audit_coords.py` | 每条坐标都能在锚点提交里读到那一行（越界、文件不存在都算失败） |
| `book/tools/check_book_structure.py` | 每章三节齐全（能回答什么 / 可验证主张 / 证据与坐标），章数与 OUTLINE 一致 |

两道门都在 CI 里逐条判退出码（不是"最后一条绿就算过"——那种写法曾经让五个脚本的失败被吞掉）。

## 这一卷不写什么

- **不写"我们的产品有多好"**：那是市场材料。这一卷写"它凭什么经得起核"。
- **不写没验过的数字**：README 里的 case 数就已经落后于夹具（`evals/cases/manifest.json` 是 20 条，README 还写着 14 条）——这一卷以夹具为准，并把这类落差当成材料讲。
- **不把"CI 绿"等同于"结论成立"**：第 7 章整章讲一个反例——CI 曾在一个只改了文档的提交上红，而真正的原因藏在并发调度的顺序里。
