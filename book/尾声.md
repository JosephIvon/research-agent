# 尾声 · 三条能带走的东西

## 一、判据先于功能

这个项目里每一个"我们做了 X"，都能追到一句"所以它会被这样判死"：

- 引用校验 → 覆盖度 0.90、有效度 1.00、扎根率 0.90、幻觉 URL 0
  （`research-agent@ef7204f src/agent/citations.py:117`）
- 预算 → 四重上界，触发即停并给理由（`research-agent@ef7204f src/agent/runner.py:74-88`）
- 注入 → 62 条确定性用例 + 端到端 case + 注入通过率=1.00 硬门槛

反过来做（先做功能、再补测试）也不是不行，但那种情况下"判据"往往会被写成
"能跑通"——而"能跑通"从来不判死任何东西。

## 二、单一来源

同一个事实只允许有一个地方定义，其它地方要么引用它、要么由测试钉住：

| 事实 | 唯一来源 | 谁在钉 |
|---|---|---|
| 证据 id | `make_evidence_id`（url+key+value 的哈希） | 引用校验 + 评测指标 |
| 工具 schema | ToolRegistry 的 JSON Schema | `test_mcp_schema_consistency.py` |
| 评测 case 数 | `evals/cases/manifest.json` | `test_readme_fixture_counts.py` |
| 书的坐标 | `book/tools/_anchor.py` 的锚点 | `audit_coords.py` |

第四行是这一卷写作期间被迫加上去的：正文里一度有 86 条坐标压根不在检查范围里，
因为工具只认一种写法（第 7 章）。**"我以为查了"和"真的查了"之间，差的就是这一类。**

## 三、把"没验"写出来

一份技术材料最容易犯的错不是"有错"，而是**让读者以为它哪儿都对**。
所以第 9 章专门列了"没验的"：真实模型效果、真实站点稳定性、前端交互、
`partial` 报告缺哪一节。

这不是谦虚，是可用性：读者知道边界在哪，才知道能拿它做什么决定。

## 留给读者的一件事

如果只能带走一句，我希望是这句：

> **CI 绿只是一个温度计，不是体温本身。**

这一卷里有三个反例：CI 在只改文档的提交上红（真因在并发顺序）、
文档数字长期落后于夹具、门禁自己漏掉了 86 条坐标。
三个都不是"检查失败"，而是"检查没覆盖到"。

检查没覆盖到的地方，绿灯和黑暗是一回事。
