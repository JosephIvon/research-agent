# 前言 · 为什么给一个"调研 Agent"写书

## 一句话

这一卷讲一个能写竞品调研报告的产品，以及**它凭什么经得起核**。

不讲话术，不讲增长，也不讲"我们用了什么模型"。
讲的是：一份报告交到用户手里时，里面每句话能不能被第三方在十分钟内查清。

## 写给谁

- **要判断这东西靠不靠谱的人**：产品、采购、技术评审。读第 1、4、6、9 章就有结论。
- **要做同类产品的人**：想知道"可核验"具体落成哪些代码形状。读第 4、5、6、7 章。
- **要接手这套代码的人**：第 2、3、8 章是结构，第 7 章是必须知道的坑。

不需要会写代码。所有结论都附一条坐标（`仓库@提交 路径:行号`），
不想读代码可以只读结论和指标。

## 为什么值得单写一卷

AI 产品最容易通过的三道自检，恰好都不构成证据：

1. **演示跑通了**——演示是挑过的输入。
2. **报告读起来专业**——文风与事实无关。
3. **用户说还行**——用户没有能力核，也没有时间核，而那正是他要买的东西。

所以这一卷每一章都落到同一个形式：**一条主张 + 一个能把它判死的量 + 一条坐标**。
判不死的量（"体验更好"）不进这一卷。

## 与另外三卷的关系

同一套方法，换一个域：

| 卷 | 域 | 真值来源 |
|---|---|---|
| 卷一《协议域卷》 | 工业协议与 SDK 绑定 | 厂商手册、PE 导出表 |
| 卷二《审计与合规卷》 | 数据审计与脱敏 | 厂区原始件、契约 |
| 卷三《代码工厂与真值链卷》 | 代码生成 | 生成物与真值链 |
| **本卷** | **AI 产品工程** | **评测夹具、引用证据、预算账** |

方法没变：把"我觉得对"换成"这里能被判死"。

## 怎么核这本书

```bash
# 1. 拿到书里引用的那个提交
git checkout ef7204f

# 2. 随便挑一条坐标，看那一行是不是书上说的那一行
git show ef7204f:src/agent/citations.py | sed -n '168p'

# 3. 让门禁把全书的坐标都核一遍
python book/tools/audit_coords.py
```

第 3 条不是装饰：写这本书的过程中，这道门自己被抓出过一个盲区——
它只统计"完整写法"的坐标，简写的一律没进检查，修好之后同一批稿子的坐标数
从 88 条涨到 174 条（第 7 章记了全过程）。

## 这一卷**不**保证什么

- 不保证这个产品在真实模型下有多准。真实 LLM 端到端需要密钥，CI 上按设计跳过
  （`research-agent@ef7204f .github/workflows/ci.yml:169`）。
- 不保证真实站点的抓取稳定性——评测走夹具，这是离线评测的固有代价。
  这两条在第 9 章逐条写清。

读一本讲"可信"的书，第一件该确认的事是：**它有没有告诉你它哪里不可信。**
