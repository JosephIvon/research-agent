# 发现召回的可测化：度量定义、金标准、判定线

> 状态：**实跑前定稿**（2026-10-29）。本文件里的定义与判定线在实跑**之前**写死，
> 跑完**不改线**；结果写在 §7（另见 `docs/decision-contract-search-e2e-2026-10.md`）。
> 触发这次工作的原因：第六/七轮实测里 Q3（句式不敏感）连续 FAIL，
> 而 Q2 只能看到**末尾**（入选名单）的质量——中间的漏斗全程不可见。

## 1. 要解决的问题（现在看不见什么）

现有五条判定线只能看到两端：

```
搜索 → [ 计划 → 搜索四段式 → 站点类型过滤 → 准入闸门 → 截 top-N ] → 入选名单
       └────────────── 这一整段全程不可见 ──────────────┘        └─ 只有 Q2/Q4 看这里
```

Q3 实测到的现象是：**两种句式选出的名单完全不重叠，但两边都是真竞品官网**
（第六轮人工核对：百度搭子/task 1/6、search 5/5；猫箱/task 7/8、search 0/1）。
"都是真的却不重合"只可能出在两个地方：

1. **搜索阶段捞到的池子就不一样**（查询词不同 → 结果不同）；
2. **池子里有很多真竞品，但截断是任意的**（同分 0.5 时按路径深度/名字排序取前 N，
   池子一变，被截进去的就是另一批）。

第 2 条在代码里是确定的：`admit_competitors()` 里 `scored.sort(key=(-score, path_depth, name))`
之后取 `max_count`，而绝大多数候选的分数**都是 0.5**（发现阶段只有"有自己的站点"这一条能拿分）。
**同分并列时用什么破平局，决定了入选名单——而破平局用的是路径深度和名字，不是质量。**

本文件要做的：把这段漏斗变成**可测**，并且能说出**每一个真竞品是在哪一步丢的**。

## 2. 度量定义（三个漏斗层级 + 稳定性）

一次运行 = 一个主体 + 一种句式。四层：

| 层 | 名称 | 含义 | 代码位置 |
|---|---|---|---|
| **L0** | 发现池 | 搜索阶段捞到的全部候选（不过滤） | `DiscoveryResult.candidates` |
| **L1** | 官网池 | 过完站点类型判定、仍被当成"产品官网"的 | `site_type == product_site` |
| **L2** | 裁决池 | 过了准入闸门（gate_passed）且分数达标的 | `DiscoveryResult.scored` 里 `gate_passed=True` |
| **L3** | 入选名单 | 截断后的最终名单 | `DiscoveryResult.selected` |

对每个主体，用**金标准**（§3）算：

| 指标 | 定义 | 回答的问题 |
|---|---|---|
| `recall_L0` | ��标准里出现在 L0 的比例 | **搜索够不够得到**（查询词与搜索引擎的召回上限） |
| `keep_L1` | 出现在 L1 的金标准 / 出现在 L0 的金标准 | 站点类型判定的**漏杀率**（把真官网判成了文章/下载页） |
| `keep_L2` | 出现在 L2 的金标准 / 出现在 L1 的金标准 | 准入闸门（规则 DSL）的**误杀率** |
| `keep_L3` | 出现在 L3 的金标准 / 出现在 L1 的金标准 | **截断丢了多少**（候选池比名额多时丢的） |
| `precision_L1` | L1 里属于金标准的比例 | 站点类型判定的**精确率** |
| `precision_L3` | L3 里属于金标准的比例 | 入选名单的精确率（≈ Q2 的自动版） |
| `stability_pool` | 同一主体同一句式**重复跑**的候选池两两 Jaccard 均值 | 搜索结果的**抖动**有多大 |
| `stability_selected` | 同上，入选名单两两 Jaccard 均值 | 名单稳不稳（这是 Q3 的"同句式版"） |

### 2.1 丢在哪一步（逐个金标准产品归因）

每个没进 L3 的金标准产品，记一条**归因**：

| 归因 | 判定 | 含义 |
|---|---|---|
| `未被发现` | 不在 L0 | 搜索没搜到它（或被去重/命名合并挤掉了） |
| `站点类型过滤` | 在 L0 不在 L1 | 分类器把它判成了文章页/下载页/目录（**漏杀**） |
| `准入闸门` | 在 L1 不在 L2 | 规则把它挡了（附 `gate_reasons`） |
| `名额截断` | 在 L2 不在 L3 | 它合格，只是排不进前 N（**排序问题**） |

**这张归因表是本文件的主要产出**：它直接回答"召回是在哪一步丢的"。

### 2.2 分母口径（不许含糊）

- `recall_L0` 的分母 = 金标准里**属于该主体赛道**的产品数（默认全部）。
- `keep_*` 的分母 = **上一层的金标准命中数**（不是总数），逐层收窄。
- 某层分母为 0 → 该层**不判**（不是 0%），记 `None`。
- `precision_*` 的分母 = 该层的**候选条数**。

## 3. 金标准（外部真值，不是代码判出来的）

金标准必须由**人核对过的真实产品官网**组成，不能由被测代码的站点类型表生成——
那正是 Q2 自证失败的原因。本项目的做法与 Q2 的人工核对同一路数，但**一次做好、反复用**：

- 文件：`evals/discovery_golden/companion_apps.json`
- 每条记录：`name` / `hosts`（该产品的已知官网域名）/ `aliases` / `evidence`（抓到的页面标题）/ `verified_at`
- 赛道：AI 陪伴 / 角色扮演（猫箱、百度搭子同属这个赛道，共用一份金标准）
- 维护方式：新增/删除条目必须写 `evidence`（页面标题或抓取状态）；**没有证据的条目不算数**

### 3.1 金标准的已知偏向（必须说在前面）

1. **它是一个下界**：只包含被核实过的产品。真实赛道里的玩家更多。
   → 对 `recall_*`：**真实召回 ≥ 测出来的召回**（测出来的偏保守）。
   → 对 `precision_*`：**真实精确率 ≤ 测出来的精确率**（没进金标准的可能是真竞品）。
2. **它偏向中文产品**：核实过程用中文搜索，海外产品漏得多。
3. **同产品多域名算一条**（如 `aijuqingapp.com` 与 `aistoryapp.com` 是 AI剧情的两个域名）。
   分母因此偏小，**召回率会略偏高**——这一条在报告里标注。

### 3.2 明确**不在**赛道里的（负例，用来验分类器不乱杀）

| 产品 | 站点 | 为什么不在 |
|---|---|---|
| 星梦岛 | `xingdaomengvpn.com` | 是 VPN 服务（"机场"），不是 AI 陪伴产品（第七轮误选过） |
| Talkie(医疗) | `talkie.ai` | 同名不同物：是 AI 医疗预约接待，不是 AI 陪伴（真站点是 `talkie-ai.com`） |
| Highrise | `highrise.game` | 3D 虚拟世界社交 App，不是 AI 陪伴/角色扮演（第七轮误选过） |
| 小爱同学 | `xiaoai.mi.com` | 通用语音助手，不是同赛道（第七轮人工核对判否） |

## 4. 判定线（实跑前定稿，阈值跑完不许改）

| 编号 | 线 | 阈值 | 测什么 |
|---|---|---|---|
| **R1** | 发现召回 `recall_L0` | ≥ 70% | 搜索+查询词能不能把赛道里的真官网捞出来 |
| **R2** | 过滤保留 `keep_L1` | ≥ 90% | 站点类型判定的漏杀率 ≤ 10% |
| **R3** | 入选保留 `keep_L3` | ≥ 60% | 截断与闸门一共留下多少真竞品 |
| **S1** | 重复稳定性 `stability_selected` | ≥ 0.5 | 同一句式重复跑，入选名单的重合度 |

**这些是诊断线，不是产品验收线**：它们的作用是**定位瓶颈**（哪一层低就去修哪一层），
而不是给产品判"合格/不合格"。真要验收，用 `docs/decision-contract-search-e2e-2026-10.md` 的五条。

**为什么阈值是这些数（理由，不是拟合）**：

- R1 = 70%：赛道里能被我核实的真官网，搜索一次至少该捞到七成——低于这个，
  说明查询词设计（"品类词" vs "产品名"）或搜索引擎覆盖不够。
- R2 = 90%：站点类型判定的漏杀是**明确的缺陷**（把真官网判成文章页），
  允许 10% 是因为"官网首页偶尔长得像文章页"确实存在。
- R3 = 60%：L1 之后剩下的都是合格候选，截断到 `max_count`（3–8 家）时，
  至少要留住六成真竞品；低于此说明**候选池与名额的关系没设计好**。
- S1 = 0.5：Q3 的同句式版。Q3 的跨句式线是 0.5；这里用同一把尺子，
  **把"句式差异"与"引擎抖动"分开**——这是本文件最关键的一步。

### 4.1 S1 与 Q3 的关系（本次测量的主要目的）

Q3（跨句式 Jaccard ≥ 0.5）连续两轮 FAIL。可能的解释有两个：

- **A**：句式处理有缺陷（任务句式 vs 搜索词句式产出不同结果）；
- **B**：搜索引擎抖动就有这么大（同句式重复跑也不重合）。

**只测 Q3 分不开 A 和 B。** 本测量同时跑"同句式重复"（S1）与"跨句式"（Q3 已有），
- 若 `stability_selected` 也 ≈0 → 主要是 **B**，Q3 的 FAIL 主要是**线定错了**
  （拿两个不同抽样比重合度，在这种抖动下不可能达标）；
- 若 `stability_selected` 高而跨句式低 → 主要是 **A**，句式处理确实有问题。

## 5. 实跑设置（成本控制）

| 项 | 取值 | 理由 |
|---|---|---|
| 主体 | 猫箱、百度搭子 | 同赛道，共用一份金标准 |
| 句式 | task（用户原话）、search（搜索词） | 与既有 4 组一致，可与第六/七轮对照 |
| 重复 | **每种句式跑 3 次** | 稳定性线需要重复；3 次可算 3 个两两 Jaccard |
| 阶段 | **只跑发现阶段**（不跑 verify/counter_evidence、不抓取） | verify+反证占了整轮 87 分钟里的约 60 分钟；召回测量不需要它们 |
| 搜索后端 | 本机 SearXNG（8888） | 与既有实跑同源，可比 |

预计：2 主体 × 2 句式 × 3 次 = 12 次发现阶段运行。

**数据无效的组不算数**（重跑）：搜索后端整轮失败（引擎集体超时/限流）、计划层报错。
判定与 `tool_e2e_search_real.py` 一致（`_group_is_invalid`）。

### 7.1 第一轮（2026-10-29 07:35–08:13，修复前）

产出：`output/recall_20261029_081343.md` / `.json`（12 次运行 = 2 主体 × 2 句式 × 3 次）。

| 线 | 指标 | 阈值 | 实测 | 结论 |
|---|---|---|---|---|
| R1 | recall_L0 | ≥ 0.70 | **0.18** | ❌ FAIL |
| R2 | keep_L1 | ≥ 0.90 | **1.00** | ✅ PASS |
| R3 | keep_L3 | ≥ 0.60 | **0.84** | ✅ PASS |
| S1 | stability_selected | ≥ 0.50 | **0.042** | ❌ FAIL |

**三个结论，一个指向搜索阶段，一个推翻了一条旧结论：**

1. **召回几乎全丢在"发现"这一步**（R1 = 18%）：18 个金标准产品，
   每次运行平均 **15 个根本没被搜到**（归因表：丢在发现 9–18 个，
   丢在站点类型 **0 个**、丢在闸门 0–1 个、丢在截断 0–4 个）。
   → 站点类型判定**没有误杀**（R2 = 100%），准入闸门也基本没误杀；
   **截断只丢 0–4 个**（R3 = 84%）。**瓶颈是搜索，不是裁决。**
2. **S1 = 0.042 说明 Q3 的 FAIL 主要是"引擎抖动"，不是"句式处理"**：
   同一句式重复跑，入选名单两两 Jaccard 只有 0.042（猫箱/search 与
   百度搭子/task 甚至是 **0.0**）。既然同句式都不重合，跨句式的 Jaccard
   （Q3，阈值 0.5）**在当前搜索后端下不可能达标**——它测的不是句式处理能力。
3. **Q2 低的机制也清楚了**：入选名单里混进了 `talkie.ai`（医疗预约，不是 AI 陪伴）、
   `hoshinoresorts.com`（星野集团，酒店）、`mewatch.sg` / `mewwallet.com`（加密钱包）——
   这些站点**有自己的域名、路径是首页**，站点类型判定看不出问题，
   而管线里"同赛道"只靠词面（`score_candidate` 的相关度）。
   → **假阳性出在"同赛道"这一层，不在"是不是官网"这一层。**

### 7.2 第一轮暴露的三个缺陷（都已修，都有回归测试）

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **统一入口吞掉了后端故障信号** | `SearchTool.search()` 用 `except Exception: continue` 把 `SearchBackendError` 吞了 → "引擎集体挂掉"被写成"没搜到"。第一轮里有一轮候选 0 却被当成**有效数据**记进了指标 | `search()` 收集 `SearchBackendError`，所有后端都拿不到结果时**抛出去**（不再返回空列表） |
| **官网子页被判成非官网 → 产品被丢掉** | 搜"星野"回来的常是 `xingyeai.com/create/login`，而"官网首页是根路径或一层"的判定把子页剔掉——**产品明明找到了却被丢**（金标准里的星野/筑梦岛反复出现这种形态） | 命中模型提名且**标题正好是那个名字**时，把 URL 归一到 host 根路径再判；标题是"星野下载-…"的下载页**不归一**（免得把门户洗成官网） |
| **"<名> 下载"查询只污染不贡献** | 模型提名竞品时用「<名> 官网」+「<名> 下载」：实测"筑梦岛 下载"**0 条**、"星野 下载"只回下载站，而下载站页面一律被剔 → 这一路查询没有净贡献 | 第二路查询改成「<名> 官方网站」（实测能捞到官网首页） |

另外：候选池为 0 时的提示语原来写"只有媒体/社区页"，与"搜到的全是媒体页"混为一谈——
现在分开说，避免把故障说成"没竞品"。

### 7.3 搜索后端本身的故障（与代码无关，但影响所有实跑）

第一轮跑完后搜索后端整体失效：google 403、duckduckgo TLS 校验失败、
brave 与 google cse 集体限流。查下来有两个坑：

1. **失效的引擎把请求的时间预算吃光**：每个失效引擎都要耗满超时（还带重试），
   排在后面的引擎**根本没机会返回** → 表现是"搜索全部 0 条"，
   而 raw 响应里的 `unresponsive_engines` 只列那几个挂掉的，看不出真凶。
2. **`yahoo` 在默认配置里是 `disabled: true`**——它其实是本机唯一还能用的引擎，
   但默认不启用（显式用 `engines=yahoo` 请求才会跑）。

处置（`searxng-settings.yml`）：禁用失效引擎（google / google cse / duckduckgo /
brave / qwant / mojeek / startpage），**显式启用 yahoo**，超时从 10s 压到 6s。

> ⚠ **因此第一轮与第二轮的绝对值不可直接比较**：引擎组合变了（原来 google/bing/
> duckduckgo 混合，现在只有 yahoo），搜到的结果集本身就不同。
> 修复的正确性由**确定性回归测试**证明（拿实测抓到的原样 URL 做断言），
> 而不是由两轮的数字相减证明。

### 7.4 第二轮（2026-10-29 08:30–09:02，修代码 + 修后端）

产出：`output/recall_20261029_090149.md` / `.json`（12 次运行，全部有效）。

| 线 | 指标 | 阈值 | 第一轮 | 第二轮 | 结论 |
|---|---|---|---|---|---|
| R1 | recall_L0 | ≥ 0.70 | 0.18 FAIL | **0.26 FAIL** | 仍不达标（引擎换了，不宜相减） |
| R2 | keep_L1 | ≥ 0.90 | 1.00 PASS | **1.00 PASS** | 站点类型判定不误杀 |
| R3 | keep_L3 | ≥ 0.60 | 0.84 PASS | **0.47 FAIL** | 见下（**金标准漏列域名**） |
| S1 | stability_selected | ≥ 0.50 | 0.042 FAIL | **0.235 FAIL** | 仍远不达标 |

**R3 从 0.84 掉到 0.47，不是代码变差，是金标准漏列了同产品的备用域名。**
归因表显示"丢在闸门"的是**星野**与**Replika**——但抓取它们的官网标题后发现，
两者都是**同一产品的另一个域名**：

| 产品 | 金标准原有域名 | 复测时被合并掉的域名 | 抓到的标题 |
|---|---|---|---|
| 星野 | xingyeai.com | `ai-xingye.cn` | 「星野 - 可定制 AI 角色设定的 AI 陪伴应用」 |
| Replika | replika.com / replikazh.com | `replika.ai` | 「Replika \| The AI Friend to do Life With」 |

管线按"同名合并成一家"把 `xingyeai.com` 合并进了 `ai-xingye.cn`（合并规则是对的），
但金标准只认其中一个域名 → 明明在 L2/L3 的产品被判成"没进闸门"。
按本文档自己的约定（**多域名 = 一条**）补全后：

- 归因变成：丢在发现 **12–15**、丢在站点类型 **0**、丢在闸门 **0**、丢在截断 **0–5**。
- R3 = 0.4236 → **0.4722**（仍 FAIL，但"闸门误杀"这一项归零了）。

> **口径更正必须留痕**：这次补域名是**看到第二轮数据之后**做的，
> 且只能**抬高**召回（补进去的域名都是管线已经搜到的）。
> 判据是"抓到的页面标题指向同一产品"，不是"补进去分数会变好"。
> 补全后的金标准**只用于第二轮及以后**；第一轮的数字是补全前算的。

### 7.5 真正的瓶颈在上游：计划本身每次都不同

第二轮跑完后回头查"为什么同一句式重复跑，入选名单几乎不重合"，
发现比"搜索引擎抖动"更靠上游的一层：**每次生成的调研计划都不一样**。

同一主体「猫箱」连生成 3 次计划：

| 次 | 实体锚定/发现阶段查询词 | 模型提名的竞品 |
|---|---|---|
| 1 | 猫箱 AI 官网 / 猫箱 应用 字节 / 猫箱 App 下载 / 猫箱 角色扮演 | 星野、筑梦岛、Talkie、Character.AI、Replika |
| 2 | 猫箱 官网 / 猫箱 App / 猫箱 AI 角色扮演 / 猫箱 开发者 | 星野、筑梦岛、Talkie、Character.AI、**PolyBuzz**、Replika |
| 3 | 猫箱 App 官网 / 猫箱 AI 官方 / 猫箱 应用商店 / 猫箱 字节 | 星野、筑梦岛、Talkie、Character.AI |

**计划一变 → 搜到的东西就变 → 候选池就变 → 入选名单当然不重合。**
于是：

- S1（同一句式重复跑的入选名单 Jaccard）测的其实是**计划抽签**，不是管线稳定性；
- Q3（两种句式的入选名单 Jaccard，线 0.5）在这种抖动下**不可能达标**——
  就算两种句式完全等价，两边各自抽到的计划也不同，交集自然是空的。
  **Q3 的阈值不改**（它是实跑前定稿的），但结论要改写：**这条线现在测不到它想测的东西**。

量化工装：`tool_e2e_plan_variance.py`（只生成计划、不搜索，一次约 30–40 秒），
产出见 §7.6。

### 7.6 计划稳定性实测

工装：`tool_e2e_plan_variance.py`（只生成计划、不搜索，一次约 30–45 秒）。
产出：`output/plan_variance_20261029_091332.md`（修复前）与
`output/plan_variance_20261029_101159.md`（修复后）。

| 指标 | 猫箱（修复前→修复后） | 百度搭子（修复前→修复后） |
|---|---|---|
| 发现/锚定阶段查询词 Jaccard | 0.139 → **1.0** | 0.256 → **1.0** |
| 全量查询词 Jaccard | 0.097 → 0.404 | 0.125 → 0.368 |
| 提名名单 Jaccard | 0.640 → 0.586 | 0.748 → 0.813 |
| 候选池输入 Jaccard（发现阶段实际会发的查询） | — → 0.627 | — →（见报告） |
| 逐字相同的计划对 | 0/10 | 0/10 |

**修法与效果**：把 entity_anchor / competitor_discovery 两个阶段的查询词改成
**由代码按模板拼装**（模型仍然决定"找谁"，代码决定"怎么搜"），
提名名单改成**去重 + 排序**（顺序不带随机性）。
发现/锚定阶段的查询词 Jaccard 从 0.139/0.256 变成 **1.0**——
"同一主体必得同一组查询"这条硬约束现在成立。

剩下的差异全部来自**提名名单**（0.586 / 0.813）——那是**模型知识**的差异
（这次多提名了 PolyBuzz、下次提名了 独响/彩云小梦），不是措辞抽签。
候选池输入 Jaccard = 0.627 与提名名单 Jaccard 基本同源：**池子还差的那部分，
是模型每次提名不同造成的**。
（10 对计划里没有一对提名名单完全相同，所以"提名相同时池子输入是否完全相同"
这一项暂无样本——提名名单稳定下来之前量不了。）

判读链条（修复后）：

```
发现/锚定查询词恒等 (J=1.0)  →  候选池输入的差异只剩"提名名单不同"
     →  候选池/入选名单仍会变（提名 J≈0.6–0.8）  →  S1 仍不可能到 0.5
```

**所以光把查询词定死还不够**：要让稳定性线有意义，提名名单也得稳定
（持久化计划 / 固定提名上限与选取规则 / 或者接受"模型知识有抖动"并改测别的）。
这是下一步的设计题，见 §7.7。

### 7.10 另外三条路，先实测再决定做不做（2026-10-31）

第三轮之后 R1 卡在 0.24，而"发现阶段丢 13–14 个"说明瓶颈在**知道要找谁**。
于是实测了三条可能的路，**结论是两条作废、一条有效**：

**① 从榜单文章里挖竞品名——作废（收益太低）。**
品类级查询搜回来的确实是榜单文章（"比猫箱更开放的AI聊天软件有哪些？实测6款平替优缺点对比"），
但抓下来看：可抓到的文章正文里只出现 **星野、Talkie、Character.AI、CHAI** 四个金标准
（模型本来就知道）；而 8 篇榜单里 **6 篇抓不到**（wenku.baidu.com 要登录、
toutiao 要 JS 渲染、zhangchengxiang.com 直接 SSL 失败）。
**做这套机制要先写抓取 + 抽取 + 二次检索，收益却只有"多找到模型已知的几个"**——不划算。

**② 让模型多提名——天花板很低。**
把提名上限从 8 放宽到 30（并明确要求"包含小众中文 App"）：

| 提示词 | 提名数 | 覆盖金标准 |
|---|---|---|
| 现状（最多 8 个） | 8 | **5–6 / 18** |
| 放宽（最多 30 个，偏向小众中文 App） | 30 | **7 / 18** |

多花 22 个名额只多覆盖 1–2 个产品——**模型的小众中文 App 知识就是天花板**。
（顺带实测到：一次要 30 个名字时，M3.1-Flash 会把 token 预算全花在思考上，
**正文为空 → 客户端返回 `None`**——就是那个"空响应"缺陷，`max_tokens` 给到 16384 才正常。）

**③ 赛道词查询（不带主体名）——有效。**
用**品类词**而不是主体名去搜（"AI 陪伴 app 官网"），能搜到**模型根本不知道**的产品：

| 查询 | 命中金标准 |
|---|---|
| 猫箱 竞品 / 猫箱 类似应用（现状，带主体名） | **0 / 18** |
| **AI 陪伴 app 官网** | **Tofai、蔚蓝陪伴** |
| AI 情感陪伴 软件 官网 / AI 伴侣 app 官网 / AI 虚拟恋人 应用 官网 | Tofai |

关键差别：**带主体名的品类查询对金标准 0 命中**（搜回来的全是文章），
**不带主体名的赛道词查询能直接命中竞品官网**——因为搜索引擎是按品类词索引的，
而主体名（猫箱）只关联到"和猫箱有关"的那几篇测评文。

于是设计成：**模型只给赛道词（track_keywords），查询词仍由代码拼**
（"AI 陪伴" → "AI 陪伴 app 官网"、"AI 陪伴 官网"；英文赛道词配英文模板）。
这与"确定性拼装"的口径一致：**模型给知识，代码给查询词**。

R1 过不了的原因现在**不是"某处有 bug"，而是三个被实测过的上限**：

1. **模型的知识上限**：提名 8 个覆盖 5–6/18，放宽到 30 个也只到 7/18（§7.10②）；
2. **搜索引擎的索引上限**：换到中文引擎后 18 个里 14 个能直接搜到官网（§7.8），
   剩下 4 个（SoulAI、AI风月、FeelinAI、Shine探光）连"逐个搜"都搜不到；
3. **名额上限**：8 个名额 vs 10+ 个合格竞品，差额记在"丢在截断"里（0–3）。

也就是说：**要把 R1 从 0.34 推到 0.70，必须同时突破上面三条**——
换模型/换引擎/放宽名额，或者**换一套金标准之外的真值来源**（例如按赛道把该品类的
全部应用都列进来，作为"全集"而不是"抽样 18 个"）。
这是**口径问题**，不是再调几行代码能解决的，得先跟需求方对齐。

> **后续（第七、八轮）**：需求方决定按上面第三条办——**把金标准扩成"该赛道全集"**，
> 实跑见 §8.7–§8.11。结论先行：全集口径下 R1 = 0.0496（289 条分母），
> 抽样口径 0.3333 **高估了约 6 倍**；同时第八轮修掉了两个站点类型缺陷
> （弱提示词误伤真官网、导航站挤掉真官网），R3 从 0.5157 回到 0.7181。
> **§7.12 的六轮数字保持原样**（同一套 18 条金标准，历史可比）。

### 7.13 结论与下一步（按优先级，2026-10-31 更新）
**这一轮做完的事**（六轮实跑，每次都有产物与归因）：

- ✅ 发现阶段的查询词改成**代码确定性拼装**（模型只提名）→ 查询词 Jaccard 1.0；
- ✅ 提名名单去重 + 排序；
- ✅ **新增赛道词发现路径**（模型给品类词，代码拼查询词）→ R1 +42%；
- ✅ 修"同一产品的多个皮各占名额"→ R3 0.78 → 0.86；
- ✅ 修"名额截断=字母序"→ R3 0.21 → 0.76、**S1 0.38 → 0.56（首次过线）**；
- ✅ 后端换成中文引擎 + 记录根因（Clash 代理没自启导致容器全断，§7.13 附注）。

**剩下的（按性价比排序）**：

1. **【口径·要先对齐】R1 的真值与阈值**（§7.12）：
   18 个金标准是**抽样**，"18 个里找到 6 个"到底算不算好，取决于这个抽样代表什么。
   现在已知 R1 = 0.34 有三个天花板（模型知识 ~0.39 / 引擎索引 0.78 / 名额 0.8–1.0）。
   要么把金标准扩成"该赛道全集"（按赛道列全，召回分母就变成全集），
   要么承认 R1 这条线在当前口径下不可达并写明原因。
   **不要为了过线而改金标准或改阈值**——那条线是实跑前定稿的。
2. **【判定】同赛道闸门**（§7.9 第 4 条）：`talkie.ai`（AI 医疗预约）、
   `hoshinoresorts.com`（星野集团，酒店）、`mewatch.sg`（加密钱包）这类
   靠词面相关度混进闸门。需要一个可核验的判据
   （竞品官网内容 vs 主体定位，或让模型按"同客群×同场景"逐条判并留理由）。
3. **【模型】空响应要显式报错**：M3.1-Flash 思考烧光 token 时客户端返回 `None`，
   计划阶段把它当成"解析失败"**静默退回默认计划**。
   要改成：空响应直接报错（不能静默降级），并对"批量提名"分批。
4. **【代码】计划可复现**：提名名单本身每次不同（J≈0.6–0.8），
   要让同一主体的计划可复现，得持久化计划或固定提名选取规则。
   （若需求是"每次跑结果一样"，这条比 S1 本身更重要。）
5. **【报告】名额截断要写进结论**：合格但没名额的有 0–3 家，
   报告里要写明"还有 N 家合格但没名额"，而不是让人以为只有 8 家。

## 8. 金标准扩成"该赛道全集"（2026-11-01，需求方决定）

第 7 节的 18 条金标准是**抽样**——"18 个里找到 6 个"到底算不算好，取决于这个抽样
代表什么。需求方决定：**把金标准扩成该赛道全集**，让召回的分母变成"该赛道有多少家"，
而不是"我们挑了 18 家"。

### 8.1 赛道边界（收录口径，先写死再采集）

**赛道**：AI 情感陪伴 / AI 角色扮演——面向个人用户，用户可以与 **AI 角色/虚拟人物**
进行**对话或互动叙事**的应用或网站。

**纳入**（三条全满足）：

1. **形态**：**有独立官网**的应用或网站（App 的官网也算）——
   这一条是硬边界：管线是**网页检索式**的，只在网页上找竞品，
   **没有官网的 App 天然不可达**（见 §8.4 的"App-only 竞品"）；
2. **功能**：能与 AI 角色/虚拟人物对话或互动叙事（角色扮演、AI 伴侣、角色卡聊天、
   互动小说、AI 宠物陪伴）；
3. **受众**：面向**个人消费者**，不是企业服务/开发者 API。

**排除**（命中任一即不收，逐条留理由）：

| 编号 | 排除项 | 例子 |
|---|---|---|
| E1 | 通用 AI 助手/大模型聊天（是聊天，但**不是"和角色对话"**） | ChatGPT、豆包、Kimi、DeepSeek、Claude、Poe、小冰 |
| E2 | AI 写作/绘画/视频/音乐生成工具 | — |
| E3 | 聚合器/导航站/榜单站/工具目录（含"AI 角色扮演"导航站） | airoleplay.ai 之类目录站 |
| E4 | 媒体/测评文章/社区帖子（非产品） | 各类"XX 盘点"文章 |
| E5 | 真实人类的社交/陪聊（非 AI） | Soul App（人类社交）、海角社区 |
| E6 | 企业客服/开发者平台/API | — |
| E7 | **同名不同物** | talkie.ai（AI 医疗预约）、hoshinoresorts.com（星野集团·酒店）、clintonhealthaccess.org（CHAI 公益组织） |
| E8 | **主体自己**（不是自己的竞品） | 猫箱 maoxiangai.com、百度搭子 dumate.cn |

### 8.2 "全集"怎么来的（以及它仍然不是真全集）

```
赛道全集 = (外部来源并集) ∪ (本管线实跑发现 ∧ 经证据核验)
```

- **外部来源**：中文 AI 导航目录分类页、中文盘点/测评文章、中文社区帖子、
  应用商店分类页与榜单、英文榜单指南与 Wikipedia、Reddit 讨论。
  每个条目都记**来源 URL**。
- **本管线发现**：从实跑产物里提取的、站点类型判定为产品官网的域名，
  按品牌归并（镜像站/汉化站合并成一家）。

**来源分层（因为来源之间并不等价）**：

| 层 | 含义 | 为什么要分层 |
|---|---|---|
| `external` | **编辑类**独立来源（导航目录/媒体/社区帖子/英文榜单/Wikipedia/Reddit）列出 | 中立来源，但覆盖偏头部 |
| `store_only` | **只有应用商店**列过（App Store / Google Play / 应用宝） | 商店搜索 API 是**抽样**（每查询返回有限条），**不是商店全量**；这一层大多是长尾产品 |
| `vendor_article` | **厂商自写的横评/SEO 稿**列出（weavai.app、aiga.io、nika.team、lumichat.ink、bladerpg.com、foreverse.cn、nieta.art、similarlabs.com、aigirlmates.com、prelulu.ai、shouldieventry.com 等） | 这些文章会**自我推荐**（写它的人的产品就在榜单里），是**有偏来源**，单列出来 |
| `sample_verified` | 早期抽样金标准里已核验的 18 条 | 已有证据 |
| `pipeline` | **只有本管线实跑发现**，外部来源一个都没列 | 这是**口径不完整度**的直接证据 |

**为什么把本管线的发现也算进去**：全集只用外部来源的话，
分母里就**不含**我们能找到的东西——那等于用"我们能找到什么"反过来定义"应该找到什么"，
是自证。算进来只会让口径更严。

**但它仍然不是真全集**：没有任何采样能枚举出赛道的全部产品，
所以 recall 测出的值**偏保守**（真实召回 ≥ 测出的值）。
本节同时报一个**口径不完整度**指标：
"只有本管线发现、外部来源一个都没列"的条目数——
它直接说明"外部来源也漏了这么多"，全集比看起来还要大。

### 8.4 全集是怎么建出来的（可复现）

三族外部来源并行采集（每个来源族一个采集器，产物落盘后合并）：

| 族 | 产物 | 条目 | 去重产品名 | 来源站点 |
|---|---|---|---|---|
| A 中文（导航目录/盘点文章/社区/媒体） | `output/_harvest_cn.json` | 549 | 259 | 77 |
| B 应用商店（App Store / Google Play / 应用宝） | `output/_harvest_store.json` | 992 | 948 | — |
| C 英文（榜单指南/目录站/Reddit/Wikipedia） | `output/_harvest_en.json` | 198 | 147 | 43 |
| 合计 | — | 1739 | 1332 个写法（归一后 1290 个） | — |

三族合并去重后 **1290 个产品名**逐个核验（每个名字：搜 → 取候选站 → 抓首页标题 → 判站点类型），
再按 §8.1 的收录口径人工裁定：

```
uv run python output\_collect_universe.py output\_harvest_cn.json output\_harvest_store.json output\_harvest_en.json
uv run python output\_build_universe.py          # → output/_universe_review.md（待裁定表）
uv run python output\_auto_decide.py             # 通过口径过滤的先标 include
uv run python output\_manual_exclusions.py       # 人工逐条看的排除/合并
uv run python output\_build_universe.py          # → evals/discovery_golden/track_universe.json
```

**自动过滤**（`output/_build_universe.py`，可复核）：主体自己（E8）、通用助手/大模型（E1）、
工具类（E2）、应用信息站/下载门户/商店页（E3）、媒体文章（E4）、
**同名不同物**（E7，页面标题里找不到品牌名）、**没有官网**（见 §8.5）。
其中"应用信息站"用了一条**数据驱动**的判据：
**同一个域名挂在 ≥5 个不同产品名下 → 它是目录站**（实测 `mwm.ai` 挂了 125 个产品名）。

**人工裁定**：459 条通过自动过滤的候选**逐条看了页面标题**，排除 159 条
（门户站/下载站 50、工具或非赛道产品 60、同名不同物 30、重复条目 15 等），
并把 12 组"同一产品多个域名"的域名并进保留的那一条
（匹配按主机名做，域名不全就会漏）。

**最终赛道全集：300 条**（`evals/discovery_golden/track_universe.json`），分层：

| 层 | 条数 | 说明 |
|---|---|---|
| `external` | 137 | 编辑类独立来源列过 |
| `store_only` | 99 | 只有商店列过（长尾为主） |
| `pipeline` | 35 | **只有本管线发现**——外部来源全漏（= 口径不完整度） |
| `sample_verified` | 17 | 早期抽样金标准（另一条里的 18 条，其中 Tofai 与" AI风月"等在本集里按同一产品合并） |
| `vendor_article` | 12 | 只被厂商自写横评列过（有偏来源） |

去重后共 **342 个主机名**（一个域名下多个产品的，按 §8.4 的约定合并成一条，
另一个名字记进 `same_host_products`——因为金标准是**按主机名**匹配的，
同域名的两个产品无法区分，统计时只能算一个）。

### 8.5 App-only 竞品：有产品、没官网（358 条）

采集到的 1290 个产品名里，有 **358 个在网页上找不到可核验的官网**
（绝大多数只在应用商店有页面）。按 §8.1 的口径 1 它们**不进 R1 分母**——
管线是网页检索式的，找不到网页的产品本来就不可能被网页检索发现，
把它们算进分母等于测"能不能发现不在网页上的东西"，恒为 0。

但这个数字本身是重要发现：**该赛道有 358 家产品只有 App、没有官网**，
对"网页检索式竞品发现"来说这是一整块**结构性盲区**（如 `AI Boyfriend Chat: iBoy`、
`AI Girlfriend: Voice Chat` 这类英文商店长尾）。要覆盖它们，
管线需要加**应用商店数据源**，而不是继续加检索词。

### 8.6 两个口径并列报，判定线不动

新旧分母不同，**数值不可直接相减**。因此测量工具支持**同一批实跑、多套分母**
（`tool_e2e_recall.py --golden-extra`），报告里并列给出：

| 口径 | 分母 | recall_L0 | 判定（线 ≥0.70，实跑前定稿，未改） |
|---|---|---|---|
| 抽样口径（原 18 条） | 18 | — | — |
| 赛道全集口径（新） | 见 §8.4 | — | — |

判定线 **R1 ≥ 0.70 / R2 ≥ 0.90 / R3 ≥ 0.60 / S1 ≥ 0.50 全部不动**，
金标准扩了**不回头改阈值**（否则就是"改尺子让自己过线"）。

分层口径由测量工具自动派生（`tool_e2e_recall.py` 的 `analyze_denominators`），
同一批实跑同时算：

| 口径 | 分母 | 含义 |
|---|---|---|
| `companion_apps` | 18 | 原抽样口径（历史可比） |
| `track_universe` | 300 | **赛道全集**（新口径） |
| `track_universe`·仅独立来源 | 137 | 只用编辑类中立来源（去掉商店长尾与厂商稿） |
| `track_universe`·独立来源+抽样核验 | 154 | 独立来源 + 早期已核验的抽样 |

### 8.7 实测结果（第七轮，2026-11-01 02:13）

同一批实跑（12 次：猫箱/百度搭子 × task/search × 3 次）换分母：

| 金标准口径 | 条目数 | recall_L0 | 判定（线 ≥0.70，未改） |
|---|---|---|---|
| `companion_apps`（抽样） | 18 | **0.3519** | FAIL |
| `track_universe`（全集） | 300 | **0.0572** | FAIL |
| `track_universe`·仅独立来源 | 137 | **0.0067** | FAIL |
| `track_universe`·独立来源+抽样核验 | 154 | **0.0557** | FAIL |

同批的 R2 = 1.00 PASS、**R3 = 0.5157 FAIL**、S1 = 0.548 PASS。

**这组数字最重要的一条**：同一个管线、同一次实跑，
**抽样口径 0.3519 vs 全集口径 0.0572——差了 6 倍**。
抽样口径不是"错"的，是**有偏的**：那 18 个产品全是赛道头部
（星野、Talkie、Character.AI、Replika…），而管线恰恰只会找到头部。
用抽样口径报召回，等于**拿自己会的题给自己打分**。

### 8.8 第七轮暴露的两个站点类型缺陷（都已修，都有回归测试）

1. **弱提示词误伤产品官网**：`PurrlyAI酒馆 - 沉浸式AI角色扮演聊天平台｜…互动体验`
   被标题里的"体验"判成文章页 → **真竞品在"站点类型过滤"这一步被丢掉**；
   猫箱官网「…探索剧情宇宙」同理。
   修法：标题提示分**强/弱**两档，**弱提示必须被佐证**（另有 ≥1 个弱提示，
   或与强提示同现）才算命中。修前那句"体验/探索"单独出现就判文章页，
   修后只有≥2 个弱提示或与强提示同现才判。
   **依据不是感觉**：把"只被弱提示命中"的候选全查了一遍——
   那些**真文章**本来就已被结构规则（域名/路径深度）拦下，弱提示只是冗余；
   去掉它不漏文章，却能放过被误伤的产品官网。
2. **导航站挤掉真官网**：`cxgn.cn` 的真实标题是「AI创作导航 - 创作与探索，
   找到任何 AI 工具」——一个 **AI 工具导航站**。但搜索结果标题里带着"星野"
   （导航站标题常列一串产品名），于是被当成"星野的产品官网"，
   又因为**域名更短**（7 字符 vs `xingyeai.com` 11 字符）在同名合并里赢了，
   把真官网挤掉 → **金标准里的星野整轮都没被命中**（归因显示"准入闸门"）。
   修法：标题含"导航/收录站/目录站"判为目录站；`cxgn.` 加进目录站域名表。

### 8.9 第八轮（修完两个站点类型缺陷后，2026-11-01 02:44）

同一套实跑设置（12 次），口径修正到 **289 条**（第八轮实测又挑出 11 条全集误收，
见 §8.10）：

| 金标准口径 | 条目数 | recall_L0 | 判定（线 ≥0.70，未改） |
|---|---|---|---|
| `companion_apps`（抽样） | 18 | 0.3333 | FAIL |
| `track_universe`（全集） | 289 | **0.0496** | FAIL |
| `track_universe`·仅独立来源 | 134 | **0.0044** | FAIL |
| `track_universe`·独立来源+抽样核验 | 151 | 0.0491 | FAIL |

R2 = 1.00 PASS、**R3 = 0.7181 PASS**（第七轮 0.5157 FAIL → 修完导航站缺陷后回来）、
**S1 = 0.4811 FAIL**（第七轮 0.548 PASS → 掉线）。

**第八轮同时把一个"假命中"清掉了**：第七轮的 CHAI 命中是
`clintonhealthaccess.org`（一个公益组织，**不是** AI 陪伴产品）——
第七轮那次 R1 里含着一个假命中，所以 0.3519 略偏高；第八轮的 CHAI 命中
才是真的 `chai-ai.com`。**更正后第七轮 R1 应记 0.3519（含 1 个假命中）、第八轮 0.3333（真命中）。**

**这一轮真正的收获是 R3**：修掉"导航站挤掉真官网"之后，
**星野这类头部竞品不再被合并丢掉**，keep_L3 从 0.5157 回到 0.7181。
代价是候选池变小（平均 105 → 70）——**被剔掉的正是那些导航站/文章页**，
池子小了但更干净。

#### 8.12.1 口径纪律（三条，缺一不可）

1. **名册与测量集互斥**。名册是**闸门的知识**，留出集才是**测量的分母**——
   同一份东西不能既是"我们告诉系统的答案"又是"系统的成绩单"。
   切分规则：只有"有官网 + 独立来源证据"的条目有资格进名册
   （`store_only` 对网页闸门没用、`pipeline` 是本管线自己发现的 = 循环论证），
   其余按 `sha1(种子|规范化名)` 分桶，桶号 <50 进名册。
   种子与规则写在金标准文件自己的 `split_policy` 里 → 可复现、可核对。
   结果：**名册 83 条 / 留出集 206 条**。
2. **通道自证条目不进分母**。C3 通道读的就是外部目录页，而金标准里有一部分条目
   **也来自那一页**——通道读到那张表再"发现"上面的产品，叫读答案。
   运行记录存 `channel_pages`，分析时把"来源正好是这些页"的条目从分母里剔掉
   （分子分母一起剔），报告里写明剔了几条。
3. **判定线一条没动，指标定义变了**。R3 ≥0.60、S1 ≥0.50 原样；
   改的是**指标定义**：从"某一次字母序结果"改成"同分下的期望值"。
   单次结果保留在报告里，便于与第八轮并排看。
   **不判的规矩不变**：分母为 0 一律"不判"，历史记录缺口径就写"不可算"
   （不用现在的默认值假装能复算）。
