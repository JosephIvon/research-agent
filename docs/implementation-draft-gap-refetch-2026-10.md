## 0. 修订记录

### 0.1 v2 → v3：判定层剥离全部语义推断（第 1 步实现后重写，`0073be6`）

第 1 步实现完做了两轮**真实 eval 报告扰动实验**，结论是 v2 的判定设计本身有问题。
不是实现偏差，是设计错。

**实验 1：模型引错证据时补抓方向系统性跑偏**

同一句「商业版 99 元/月」，真实证据里 `pricing = 商业版 99 元/月` 确实存在：

| 引用 | 违规 | 判定 | 补抓方向 |
|---|---|---|---|
| pricing（引对） | 无 | 不进入补抓层 | — |
| limitations（引错） | ungrounded | eligible | `faq/limits/help/support` ❌ |
| features（引错） | ungrounded | eligible | `features/guide/docs/功能` ❌ |

正确答案在 pricing 页。根因：维度归因取自**被引用证据的 key**，而模型引错 id 时
维度归因必然跟着错 → 命中率恒为 0，却要全额支付抓取与抽取成本。

**实验 2：那张维度同义词表在开放领域必然漏，而且已经在漏**

抽取器的「标准 key」只是**提示词建议**，无任何强制——`extract_key_info` 的 JSON schema
里 `key: {"type": "string"}` 没有 enum，措辞是「请**优先**使用以下标准 key」。
模型写出 `pricing_tier_v2`、`rate_limits`、`sla` 之类一律落进 unknown，
补抓方向退化成通用词。表随领域增长而增长，而开放领域没有边界。

更糟的是意识到自己在**用第二个语义推断（维度表）去补第一个语义推断（数字匹配）**。
v2 先卡维度（实验 1 证伪），改而放宽成「同站 + 数字存在即已有」——
那又是一次语义推断：99 可能是限流而不是定价。

**v3 的处理：判定层不再包含任何语义推断。**

| | v2 | v3 |
|---|---|---|
| 判定依据 | 数字 + 维度词表 | 违规类型、站点归属、缺口条数、额度 |
| 词表 | `_DIMENSION_ALIASES` 45 条 + `_DIMENSION_TERMS` 9 组 | **全部删除** |
| `boost_terms` | 由维度推导 | **删除**，选页归第 2 步 |
| `already_available` | 语义推断产物 | **删除** |
| 候选排序 | 语义维度 | **缺口条数降序**（结构信号） |
| 原因码 | 4 个语义码 | 全部结构性 |

代价要如实说：删掉 `already_available` 后，扰动实验中 eligible 从 7/12 升到 **8/12**，
补抓开销上升。换来的是判定在开放领域不会因词表缺词而**静默失效**——而后者从外部
完全看不出来。

**缺失数字从决策降级为观测**：`missing_numbers` 仍进决策对象，但判定过程从不读它。
它的用途是抓完之后回看这些数字有没有出现在新证据里——**那是度量不是决策**，
对应 §6 的 `resolved_gap_count`，且对开放领域免疫。

### 0.2 `discover_research_links` 静态权重表：**曾未经检验，已审计并修复**（`21467f9`）

v2 打算直接复用它当补抓选页依据。审计后发现它本身经不起检验
（以下描述针对**修复前**的代码，见 `21467f9^:src/crawler/web_crawler.py:278-310`）：

1. **零分即丢弃是硬边界**：`if score <= 0: continue`。匹配不到任何词条的链接
   **永远不会被考虑**——`/enterprise-seats`、`/sla`、`/security`、`/compliance`
   全是 0 分。表外的页面不是排在后面，是**不存在**。这把「不知道」伪装成「不存在」。
2. **首匹配即 `break`，顺序即优先级**：同时命中 pricing 和 api 的 URL 只按先命中的算。
3. **裸子串匹配误伤**：`any(term.lower() in evidence ...)` 让 `api` 命中 `rapid`/`capital`，

4. **权重编码了未经检验的业务假设**：pricing > docs > models > api 这套排序
   对 SaaS 竞品调研成立，对医疗/金融/工具类不成立，且硬编码在函数里改不动。

**这四项已全部修复（`21467f9`，第 1.5 步）**，逐项对应到当前代码：

### 0.3 v1 中被证伪的两点（v1 → v2 的起因）

**① 「补抓后重建 EvidenceStore 再校验」是假闭环。**

v1 §4.3 写的是「补抓成功则追加 `extracted_data`、重建 `EvidenceStore`、跑第三次校验」。
这是错的。`verify_report` 的扎根判定**只看该句实际引用的证据**
（`citations.py:768-778`：`sources = [store.get(eid) for eid in cited]`）。

报告里那句「专业版 99 元/月 [e:旧ID]」，即使补抓到了新证据，
只要原句还引用旧 id，`ungrounded_claim` 照旧失败。
**必须先重新生成报告、让它引用新证据，校验才有意义。**

**② 「建一个 TaskBudget 就能护住补抓」也是假的。**

v1 §5.1 建议在 `_refetch_for_gaps` 内部建 `TaskBudget`。但 legacy 的
`CoordinatorAgent.extract_key_info` 调用是 `achat_completion(prompt, temperature=0.1)`
（`mvp_workflow.py:235`），**没有传 `usage_sink`**，签名里也没有 budget 参数。
`usage_sink` 默认为 None 时，客户端连 `response.usage` 都不读（`src/llm/__init__.py:84`）。

对照 react 路径：`tool_specs.py:158-165` 里 `extract_facts` 显式传了
`usage_sink=_usage_sink if budget is not None else None`。
建一个没人往里记账的 `TaskBudget` 对象，不构成任何预算守卫。

### 0.4 评审问题 C：`gap_refetch` 的 SSE 事件**要接三处**，不是「无需改前端」

v2 原话是「复用现有 `agent_step` 事件，不改前端」。评审指出这是错的，我逐条查代码，
**确认评审成立**——「不改前端」只在**复用 `agent_step`** 这个前提下才成立，
而选哪种事件名正是待决策项（§5.4），一旦选「新增独立事件名」，三处都得接线：

| 位置 | 行为 | 后果 |
|---|---|---|
| `mvp_workflow.py:679-683` `_emit` | 未登记事件名 **raise `ValueError`**，不是静默丢弃 | 发新事件名会**直接抛异常** |

所以事件选型（§5.4）必须在第 4 步**之前**定，不能拖到写代码时随手决定。

> **已决（§5.4）：复用 `agent_step`，三处白名单零改动。**

## 1. 要解决的问题

当前引用校验闭环在 `src/workflow/mvp_workflow.py:848-885`：

```
生成报告 → verify_report
  ↓ 未通过
format_violations → 带违规清单重生成一次（复用**同一个** evidence_store）
  ↓ 仍未通过
_mark_low_trust → 挂低可信标记，照常交付
```

重生成复用的是同一个 `EvidenceStore`（`mvp_workflow.py:867-875`），
结构上不可能取到新证据。证据真缺时，闭环闭不上。

Scout 的做法是让 reviewer 输出结构化缺口清单并定向补搜。
可借鉴的**不是它那套模糊的 gap 描述，而是补搜这个动作本身**——
本项目的违规信息比它精确得多。

## 2. 对外部建议的三处修正

### 2.1 第一版只处理 `ungrounded_claim`（这是产品策略，不是因果判断）

| 违规类型 | 第一版行为 | 说明 |
|---|---|---|
| `unknown_citation` | 不触发补抓 | 引用 id 无效，属于幻觉 id |
| `uncited_claim` | 不触发补抓 | **这是范围收窄的选择**，不是说它必然不缺证据 |
| `ungrounded_claim` | 触发判定 | 数值在所引证据里找不到 |

`uncited_claim` 只说明「这句没引用」，**不等于「它说的数值一定已在证据库里」**——
也可能是模型写了个证据库里根本没有的数。本版不处理它，是为了控制成本与范围，
后续是否支持应由独立评测决定，而不是靠推理拍板。

### 2.2 补抓对象不是「搜索」，是同源站内页

外部建议写「调用 web_search 拉取新证据」——那是开放网络问答场景（Scout 的场景）。
本项目输入是**用户指定的竞品站点**，正确动作是在已发现的同源链接里多抓几页。

现有发现逻辑在 `src/crawler/web_crawler.py` 的 `DEFAULT_PRIORITY_TIERS`（`:34-47`），
是一张**静态关键词权重表**（pricing=100 / docs=90 / models=85 / api=80 /
workflow=65 / console=55 / faq=45）。这套打分与缺口内容无关，是需要改造的地方。

> 注：**修复前**（见 `21467f9^` 的 `web_crawler.py:278-310`）这张表还伴随
> 「得分 0 直接丢弃」的硬边界；该问题已按 §0.2 修掉。
> 但**打分与缺口内容无关这一点没变，也变不了**——权重表是站点级的先验，
> 而缺口是句子级的。补抓阶段复用它 = 沿用这个先验。

### 2.3 legacy 路径没有预算守卫

`TaskBudget` 只在 `_run_react_mode` 内构造（`mvp_workflow.py:989`）。
legacy 路径没有 token 计量、没有成本账本、没有 `PARTIAL` 终态。
§0.3② 已说明：这不是「加个对象」能解决的。

## 3. 核心设计

### 3.1 完整闭环（v1 遗漏的第三次生成已补上）

```
① 第一次报告生成
② 校验失败 → 带违规清单重生成一次
③ 第二次校验仍失败 → plan_gap_refetch 纯函数判定，记录原因
       │ 不合格 → 沿用现有低可信交付
       ↓ 合格
④ 定向发现同源候选页 → 安全抓取 → 完整注入防护 → 抽取新证据
⑤ 合并证据 → **第三次报告生成**（提示词明确指出未解决违规项，要求优先使用新增证据）
⑥ 第三次校验 → 通过则正常交付，否则低可信交付
```

**报告生成至多 3 次，补抓至多 1 轮。** 第三次生成是一次受限定向修复，不是递归循环。

注意 ⑤ 的措辞边界：**不得把新证据当成自动支持原有句子的依据**。
必须让模型重新选择引用，校验才有意义（§0.3①）。

### 3.2 判定：纯函数，输出可解释的结构性判定结果

不返回 `Optional[RefetchPlan]`——`None` 无法回答「为什么不补抓」，空转率无法观测。

```python
@dataclass(frozen=True)
class GapRefetchCandidate:
    competitor_url: str          # 站点标识（netloc），不是页面 URL
    competitor_name: str
    missing_numbers: List[str]   # 仅供观测，判定过程不读
    claim_count: int             # 该站点上的 ungrounded 数量 → 排序依据
    per_candidate_pages: int = 1

@dataclass(frozen=True)
class GapRefetchDecision:
    eligible: bool
    reason: str
    candidates: List[GapRefetchCandidate]
    page_budget: int
    skipped: Dict[str, int]        # 每种跳过原因的计数
    seen_violation_types: Dict[str, int]

def plan_gap_refetch(
    violations: Sequence[Dict[str, Any]],
    store: EvidenceStore,
    target_sites: Optional[Sequence[Dict[str, Any]]] = None,
    max_pages: int = 3,
) -> GapRefetchDecision:
    """纯函数：不联网、不调 LLM、不改全局状态。"""
```

**这个函数刻意不回答「该抓哪一页」**（见 §0.1 与 §0.2）。
它只用结构信号：违规类型、站点归属、缺口条数、额度。

### 3.3 判定树：全结构性

```
第二次校验仍失败
  ↓
筛选 ungrounded_claim（另两类不触发，见 §2.1）
  ↓
逐条解析结构化字段
├─ 缺 missing_numbers / cited_ids → violation_not_structured（不猜，不解析中文句子）
├─ cited_ids 在 store 里查不到    → unresolvable_citation（不同源，不猜）
├─ 所引证据跨站点 / 无来源        → ambiguous_target
├─ 来源站点不在 target_sites 内   → ambiguous_target
└─ 归属唯一 → 按站点聚合，缺口条数累加
  ↓
按 claim_count 降序（同数按站点标识排序，保证可复现）
  ↓
额度 = min(max_pages, 候选数)；不足时至少各 1 页
```

**不做的事**：不按证据 key 归维度、不按维度推导关键词、不判断「数值是否在别处已有」。
三者都需要语义先验，在开放领域无法穷举（§0.1）。

原因码全部是结构性的，便于按 `skipped` 分布反查是哪一环出问题。

### 4.5 测试与评测（+约 250 行）

| 类别 | 必须验证的行为 |
|---|---|
| 纯函数 | 三类违规按第一版策略分流；归属不唯一/跨站/超范围安全跳过 |
| **语义隔离** | **改证据 key 判定结果不变；同站多一条含同数字的证据判定结果不变** |
| 聚合 | 同站点多缺口聚合成一个候选，缺失数值去重，claim_count 正确 |
| 排序 | 缺口多的竞品优先；并列时按站点标识确定性排序 |
| 完整闭环 | 补抓 → 新证据 → **第三次生成引用新证据** → 第三次校验通过 |
| **防假闭环** | 只重建证据库、不重新生成报告时，测试必须能识别该路径修不好原引用 |
| 开销护栏 | `unknown_citation` 不触发；各硬上限生效；无候选页时不调用抽取 LLM |
| 安全 | 新页面注入被中和/整页丢弃；跨域与异常重定向不能绕过 SSRF 边界 |
| 失败恢复 | 单页失败不影响其他页；上限触发后停止补抓并按既定策略降级 |
| 证据与状态 | 完全相同三元组去重；**同页两次 LLM 抽取结果不同也能各自入库** |
| 回归 | 无候选、补抓未命中、第三次校验失败均保留原低可信交付语义 |
| 选页策略 | **跨行业用例**（SaaS / 云 / 金融 / 医疗 / 工具）验证静态权重表不误杀、不漏杀 |
| **夹具替身** | 补抓路径在 `FixtureSiteSource` 里真跑起来；零补抓的用例会红（防 §0.5 的 D2） |

> **幂等性表述收窄**：`EvidenceStore` 按 `sha256(url, key, value)` 去重
> （`citations.py:168-175`），只能保证**完全相同的三元组**不重复入库；
> 它**不保证**同一页两次 LLM 抽取产出相同条目。

评测侧新增三类场景，用来算收益而不是证明「代码跑通」：

1. **真缺口可修复**：首页缺定价数值，`/pricing` 页有 → 补抓后校验通过
2. **无效候选**：`unknown_citation`，或无可发现的同源页 → 断言零补抓
3. **补抓不命中**：有候选页但页面无所需数据 → 只试一轮，低可信交付，上限不超

> **场景 1 必须断言「确实补抓了」，不能只断言最终校验通过。**
> 因为 §0.5 的 D2：夹具一旦继续返回 `discovered_urls: []`，补抓就是零页，
> 而「零页」同样可能让报告保持原样、校验结果不变——**断言只写「校验通过」
> 就会因为错误的原因通过**。断言至少含：`refetched_pages >= 1`、
> 报告里出现**新证据 id**、`resolved_gap_count >= 1`。
> 同类教训已有先例：跨域测试曾因假域名 DNS 失败而「通过」，已改用可解析域名。

核心指标：**真缺口修复率**、**无效补抓率**、额外 LLM 调用数/页数/耗时/估算成本、
第三次校验通过率。13 条现有用例继续作为原基线，新场景按「基线版本化不滚动」升版。

## 5. 待决策项

### 5.1 硬上限的具体数值 —— **已决**

**指什么**：总补抓页数（含首页重抓）、单页抽取次数、单次 LLM 调用的 `max_tokens`。
它们的作用是「在 `usage_sink` 接线完成前，先给这条新路径一个不会失控的天花板」
——因为 legacy 抽取路径没有 token 记账（§0.3②）。

**决定（已拍板）：3 页 / 单页 1 次抽取，但把 3 拆开说清楚——1 页首页重抓 + 2 页内容页。**
理由：首页重抓是**发现阶段的输入**，不产生 LLM 调用；把它和内容页混算在一个
「3」里，等于让发现开销挤占实际取证的名额。拆分后语义无歧义，
日后要调内容页数时不用重算整条链。

> 仍然成立的前提：**拿到真缺口修复率数据之前不要调大**。
> 合成夹具命中一次不代表真实站点也能命中。
>
> 并且要承认这条上限**只能限时间、不能限 token**（legacy 无记账）：
> 「整批墙钟上限」与「单次 `max_tokens`」不是可选项，
> 是这条路径在第二层记账接线完成前唯一的成本闸门。

**三个数值定稿（零新常量，全部复用既有值）：**

| 闸门 | 取值 | 出处与理由 |
|---|---|---|
| 整批墙钟 | `AGENT_WALL_CLOCK_BUDGET = 180` | `src/agent/config.py:17`。补抓整批（发现 + 抓取 + 抽取 + **一次完整报告生成**）必须落在一个任务级预算内；这是全仓已有的唯一墙钟闸门，复用它不新增第二套语义 |
| 单页抽取 `max_tokens` | `AGENT_BUDGET_CONVERGE_MAX_TOKENS = 2048` | `src/agent/config.py:27`。**实测**：`max_tokens=1024` → 425 字符 / 4.1s；`2048` → 641 字符 / 3.7s；**两者都没有 `finish_reason="length"` 截断信号**。补抓抽的是单页结构化要点，2048 够用且不比 1024 慢 |
| 报告重生成 `max_tokens` | `REPORT_MAX_TOKENS = 16384` | `mvp_workflow.py:356`，其 docstring 记录了 4096 组 2/6 被 `finish_reason="length"` 砍掉正文（被砍的报告**不是空的**，只是少了结论章节，更隐蔽）。补抓路径的重生成就是一次普通报告生成，没有理由给更小的预算 |

**为什么不新造常量**：三个值都是「这条路径本来就会走的既有调用」的预算。
为它们单开一个 `GAP_REFETCH_*_MAX_TOKENS` 只会制造第二处需要同步维护的数字，
而实测并没有显示这条路径需要**更小**的上限——在拿到真缺口修复率数据之前，
给它更紧的闸门只会把「命中率不够」误判成「上限太小」。

### 5.2 第三次校验仍不过怎么办 —— **已决**

**指什么**：第一次校验不过 → 补抓 → 重生成 → **第三次**校验仍不过时，任务怎么收尾。

**决定（已拍板）：照常挂低可信交付，并在报告里注明「已尝试定向补抓但未命中」。**
沿用现有 `_mark_low_trust`（`mvp_workflow.py:589`），**不新增终态**。三条理由：

1. 它的语义本来就是「校验没过就显式挂低可信」，第三次没过只是同一状态第三次出现，
   不是新情况。新增终态会让下游（前端、DB、告警）多一套要认的状态。
2. 它的守卫写在函数内部而非调用方（`mvp_workflow.py:595` 的注释说明了理由），
   复用它天然继承「不静默交付」这条硬要求。
3. **它是可观测的**：低可信标记里会带具体违规项，用户能看到「补抓了但没命中」，
   而不是收到一份看起来正常的报告。

（未采纳的备选：参照 `research-agent-lab` 的 `claims_report.py`，
校验不过就不让声明进报告。那是更硬的产品口径，属**产品决策**——
需要单独拍板是否要那个强度，本次不纳入。）

### 5.3 记账字段形态 —— **已决（`resolved_gap_count` 的回填时机除外）**

**指什么**：§6 那张字段表是否够用，以及谁在什么时候填。

**决定：现在定死全部字段的形态与填充时机，只留 `resolved_gap_count` 延后回填。**

| `planned_pages` / `candidate_count` | 发现后 | `candidate_count` 是 §5.5 第 1 步要的**分母侧信息** |
| `budget_truncated` | 候选多于额度时 | 区分「排序错」与「发现漏」的关键，见下 |
| `fetched_pages` / `blocked_pages` / `failed_pages` | 抓取后 | `blocked` 与 `failed` 必须分开：前者是注入防护在起作用，后者是网络问题 |
| `new_evidence_count` | 抽取后 | |
| `remaining_violation_count` | 第三次校验后 | |

> `budget_truncated` 值得单独强调：它是区分 §5.5 第 1 步三种失败模式里
> **「排序错」与「发现漏」**的唯一信号。正确页在候选里但被额度挤掉 → 调预算；
> 正确页压根不在候选里 → 改发现逻辑，与权重表无关。没有这个字段，
> 两种情况都会退化成同一个 `resolved_gap_count = 0`。

### 5.5.1 第 1 步的上半段已完成：**权重表排序质量实测**（24 站 / 5 行业，不依赖 LLM）

排序质量是「网站结构 + 打分函数」的函数，与生成模型无关，所以这一半**不需要真实 LLM**。
实测用普通 HTTP 取 24 个真实竞品站（devtool / saas / collab / fintech / cloud / health），
首页同源链接池上限 25，并发 6，UA 自报身份。

**主指标用「top-K 内是否含定价类路径」**，不用自造 oracle。原因见下方踩坑记录。

| 方法 | top-1 命中 | top-2 命中 | top-4 命中 |
|---|---|---|---|
| **当前权重表** | **16/19 (84%)** | **16/19 (84%)** | **16/19 (84%)** |
| 旧行为 `min_score=1` | 16/19 | 16/19 | 16/19 |
| 文档顺序（不排序） | 2/19 (11%) | 4/19 (21%) | 6/19 (32%) |

**结论一：权重表值得保留。** 它把定价/套餐页排进 top-1 的比例是 84%，
文档顺序只有 11%。聚合 recall/precision 曾一度显示「文档顺序更好」，
那是我自造 oracle 不合格的产物（见下方踩坑），不是真实结论。

**结论二：§0.2 的审计修复对「找到定价页」这件事零收益，但对 oracle 口径收益很大。**
两把尺子给出两个都成立的故事：

| 口径 | table | table_min1 | 说明 |
|---|---|---|---|
| 定价路径（可判读） | 16/19 | 16/19 | **无差异**——定价词本来就在词表里，永远命中 |
| `recall_loose@4`（含数字） | 0.143 | 0.056 | **+0.087**，修复把 0 分页从「不存在」变回可排序 |

不矛盾：审计修复救的是**词表外**的页（`/enterprise-seats`、`/sla`、`/security`），
定价页从来不需要它。所以审计**不是错的**，只是它的收益不在定价路径这个指标上。

**结论三：`excluded_segments` 有真实假阴性——这是本轮测出的代码缺陷。**
19 站里有 9 个「含定价数值却被排除」的页面，其中 **2 个是明确的误伤**：

| URL | 命中的排除词 | 判定 |
|---|---|---|
| `plaid.com/products/auth` | `auth` | ❌ **误伤**——Plaid 的 Auth 产品页，竞品能力核心页 |
| `brex.com/product/business-account` | `account` | ❌ **误伤**——Brex Business 产品页 |
| `posthog.com/careers`、`digitalocean.com/careers` | `careers` | ✅ 正确 |
| `plaid.com/legal`、`linode.com/legal`、`monday.com/w/departments/legal` | `legal` | ✅ 正确 |
| `wise.com/cn/account` | `account` | ✅ 正确（账户页） |
| `brex.com/resources/future-of-procurement-register` | `register` | ⚠️ 边缘（resources 页） |

根因：`_is_excluded`（`web_crawler.py:80`）按**任意**路径段 token 精确匹配，
不区分它是首段还是子段。`/auth` 该排除，`/products/auth` 不该。
**这条缺陷是 §0.2 那次审计引入的，16 条合成用例抓不到它——真实站点才暴露。**

**结论四：词表确实是 SaaS 形状的（§5.5 的原假设得到印证）。**
唯一像样的失败样本是 `webmd.com`：top-2 选了 `/facebook-groups` 和一条乳腺癌视频页。
它 25 个候选里有 12 个含定价数值，权重表一个都没捞到——医疗类词汇表里没有对应词。

**已知局限（结论必须连着读）**：

- **19/24 站可达**。gitlab / dropbox / vultr / healthline / zocdoc 首页取不到（反爬或纯 JS）。
- **用普通 HTTP 而非生产路径的 Playwright** → JS 注入的链接会漏，**本测量低估生产表现**。
- **候选池只取首页同源链接**，不做二层展开 → 测的是「表能否在首页链接里排对」，
  不是「表能否跨层找到深层定价页」。
- **n = 19 < 20**，按本节预注册规则（「≥20 次真实运行且命中率低于中位数一半才考虑整表覆盖」），
  **本次数据不足以支持换表**。但它**足以支持修 `_is_excluded`**——那是明确误伤，不需要等样本量。

#### 踩坑记录：自造 oracle 让结论反转了一次，值得留着

第一轮用「页面含数字」（loose）与「数字 40 字符内有货币/单位词」（strict）当 oracle，
聚合结果是 **`doc_order` 的 recall/precision 全面优于权重表**，差到 `@4` recall 0.206 vs 0.110。
差点据此写成「权重表不如文档顺序」。

两个问题：
1. **loose 饱和**：19 站的中位命中率 **1.00**（几乎每个页面都有数字——年份、版权、版本号），
   recall@4 的理论上限只有 4/24≈0.17，对方法差异不敏感。
2. **strict 是错的代理**：它把「99.99% uptime」「白皮书省 $X」也算成定价页。
   文档顺序的前 4 条恰好是主导航，那些页面满是营销数字 → precision 虚高。

**换成人能直接判读的「top-K 是否含定价类路径」后，结论直接反转。**
教训：**当自造指标与可判读事实冲突时，先怀疑指标。** 这与本项目此前
「测试因错误原因通过」「truncation_rate 恒为 0」是同一类错误的变体。

（另：测量脚本本身犯过一次同类错——第一版漏存 `recall_strict`，
只存了 `precision_strict`，导致 strict 口径无法事后补算（有序列表没落全盘），
必须带修正重爬整批 24 站。第二版已把有序列表与逐页 oracle 全量落盘。）

| 失败模式 | 现象 | 修法 |
|---|---|---|
| **排序错** | 正确的页在候选里，但排在 `page_budget` 之外没被抓 | 调预算或调表 |
| **发现漏** | 正确的页根本不在候选里（同源过滤 / 排除集 / 锚点缺失） | 改**发现逻辑**，与权重表无关 |
| **本来就没有** | 站点任何页面都没有该数值 | 无解，属正常，应计入分母做基线 |

一个总命中率把这三种平均掉，等于三个不同的结论互相抵消。
所以在谈命中率之前，先记 `chosen_pages` / `candidate_count` / `budget_truncated`
（是否有正确候选被预算截断）三个字段。

### 5.5.2 第 1 步的下半段已完成：**真实 LLM + 真实站点**，三种失败模式分布

2026-10-15 用真实 MiniMax-M3 跑 5 组、共 10 个真实竞品站（15 次 LLM 调用）。
每组：真实抓取 → 真实 `extract_key_info` → 真实 `generate_report` → `verify_report`
→ 拿到 `ungrounded_claim` 的 `missing_numbers` → 再用首页同源链接池（上限 40）
逐页定位每个缺失数字 → 分类。**不依赖补抓功能是否已实现**——
判定三种模式只需要「候选集」+「oracle」，两者都是现成的。

**先说最重要的结论：原始「缺失数字」列表里 40% 是噪音，必须先剔掉才能谈分布。**

| 层级 | 数量 | 说明 |
|---|---|---|
| `ungrounded_claim` 缺失数字总数 | 20 | 5 组里 3 组触发，共 6 处违规 |
| 其中小整数（≤3 位） | 16 (80%) | `1` `2` `5` `7` `8` `24` `360` |
| 其中**无法定位**（命中 0 页 或 命中率 ≥50%） | 8 (40%) | 数字在半数以上页面都出现，指不到具体页 |
| 剔除噪音后的可用样本 | **12** | 下表基于这 12 个 |

**剔除噪音后的分布（n=12）：**

| 失败模式 | 数量 | 占比 | 补抓能否影响 |
|---|---|---|---|
| **本来就没有** | 5 | 42% | ❌ 无解——模型编的数字，站点上没有 |
| 排序错 | 3 | 25% | ✅ 调预算/调表 |
| 发现漏 | 1 | 8% | ✅ 改发现逻辑 |
| would_fix（数字已在已抓页，但要靠重新抽取才进证据） | 3 | 25% | ⚠️ 换页无用，得重跑抽取 |

**补抓真正能影响的部分 = 排序错 + 发现漏 = 4/12 = 33%。**
最大的一块（42%）是 `absent`——模型凭空编的数字，**补抓无能为力**。
（注意别把这句话读成「系统也修不了」：`absent` 类缺口恰恰能被**重生成**修好，
模型手里有完整证据表，可以换一个**有据可引**的数。证据见 §5.8。）

**这改变了整个方案的前提判断。** 原草案默认「缺口 = 站点上某处有正确数字，只是没抓到」。
实测显示**近一半的缺口根本不存在**。而且这些缺口的特征很典型：
`99043013`（法国格式电话号码，brex/wise 报告里都出现）、`4000`、
以及大量「支持 N 个集成」式的凭空计数。

**由此引出一个必须先回答的问题：什么样的缺口才算「可补抓的缺口」？**
当前 `ungrounded_claim` 触发条件是「句中任一数字不在所引证据原文中」，
它把 `1`、`24` 这种小整数一并算进来——而这些数字在任何页面都存在，
既无法定位，补抓也修不了。**在定义清楚之前，第 2~4 步的 `page_budget`
调大调小都没有意义。** → 答案见 §5.8。

#### 这一轮同时证实 / 推翻的东西

- **证实：真实 LLM 会产生 `ungrounded_claim`**（3/5 组，6 处 / 15 次调用）。

- **推翻：「三种失败模式分布」可以在少量真实运行上直接读出。**
  20 个缺失数字里 40% 是无法定位的噪音，原始分布（35%/35%/5%/25%）
  **是假的**——它把小整数当成信号。同 §5.5.1 的教训：自造指标不可信。

- **n = 12 可用样本，来自 5 组运行**，远不足以谈稳定分布；只能回答

#### 两处工装自身的坑（都记在这里，别重蹈）

1. 第一版用**原始子串**在页面文本里找数字 → `99043013` 在页面上是

   一次判 `absent` 一次判 `ranking_miss`。改成调用生产同款的
   `extract_numbers`（与 `verify_report` 同一套归一化）后分布才稳定。
2. `competitors` 少给 `name` 字段直接 `KeyError`——生产里这个字段来自
   `infer_competitor_name(url, facts)`，抄形状时漏了。

### 5.5.3 候选池加深实测：**「42% 偏高」这条自我修正不成立**

§5.5.2 自己写下了一个局限：「候选池只取首页同源链接 → 深层页面被计入 `absent`
→ 42% 偏高，实际比例应更低」。**这句话得自己验证**，不验证就写进文档等于
给后来人一个假的下限。两轮实测（仍然 **0 次 LLM 调用**，复用同一批 20 个缺失数字）。

#### 第一轮：二层展开 + 换生产 Playwright（结论只能用于 `absent` 那一列）

**5 个 `absent` 全部仍是 `absent`**，包括池子真正加深的站：

| 站点 | 数字 | 池（旧→新） | 判定 |
|---|---|---|---|
| wise.com | `99043013` | 40 → **100** | absent → **absent** |
| www.brex.com | `99043013` | 40 → **83** | absent → **absent** |
| www.figma.com | `4000` | 40 → 40 | absent → **absent** |
| www.teladoc.com | `5` | 40 → 40 | absent → **absent** |
| www.webmd.com | `360` | 40 → 40 | absent → **absent** |

**但这一轮有三个缺陷，整体分布变化不能采信：**

| # | 缺陷 | 证据 |
|---|---|---|
| (a) | **4/8 站二层是 0 条**，加深只对 3 个站真正生效 | 诊断：figma 的 12 个 seed **全部抓取成功**，二层仍是 0——根因是第一层在 40 条就截断，seed 页的链接基本都落在这 40 条里 |
| (b) | **两个变量同时动了**（深度 + 抓取保真度） | webmd 池子大小没变（40→40），命中率却 92%→18%、90%→22%、98%→55%、60%→15%。**当时的归因（Playwright 保真度）已被 §5.5.4 推翻——真凶是提取器** |
| (c) | **linode.com 在 Playwright 下首页不可达**（普通 HTTP 可达） | n 从 20 掉到 18；grammarly 也只有 2/40 页能取到数字，疑似反爬 |

(b) 的后果比看上去严重：webmd 那几个数因为命中率跌破 50% 而**跨过了噪音阈值**，
可用样本集本身被改写（n 12→14），于是「补抓能影响 33%→43%」这个变化
**无法归因于加深**。可比的只有 `absent` 那一列。

#### 第二轮：只跑 absent，第一层上限提到 120（干净结论）

只跑 5 个 `absent` 站，把「深度」限制在回答一个问题上：*更深的池子会不会翻出它们*。

| 站点 | 数字 | 一层 | 二层 | 池 | 含数字页 | 判定 |
|---|---|---|---|---|---|---|
| wise.com | `99043013` | 105 | 55 | 160 | 63 | **absent** |
| www.brex.com | `99043013` | 49 | 35 | 84 | 49 | **absent** |
| www.figma.com | `4000` | 91 | 55 | **146** | **108** | **absent** |
| www.teladoc.com | `5` | 55 | 0 | 55 | 43 | **absent** |
| www.webmd.com | `360` | 120 | 40 | 160 | 96 | **absent** |

**5/5 全部仍为 `absent`。** figma 那行最硬：池 40→146、含数字页 34→108（4 倍），
`4000` 依然一次都没出现。

**结论：42% 不算高估。** 这些数字在站点上确实不存在，是模型编的。
§5.5.2 那条「实际比例应更低」的自我修正**作废**，42% 按实测保留。

#### 剩下的局限（不推翻结论，但要连着读）

- **抓取失败率 33%**（409 成功 / 201 失败，单次尝试 8s 超时）。抓不到的页
  无法判定。生产默认是 30s × 3 次重试，这里为了在 5 站 × 160 页内跑完而收紧。
- **teladoc 二层仍是 0**（第一层只挖到 55 条就到底），它的 `5` 属于单位数，
  本来也不可定位。
- **仍未验证的是另一件事**：`absent` 类缺口能不能被**重生成**修复。
  §5.8 的结论是能——工作流夹具里模型自己把数字换了。**这两件事不矛盾**：
  数字不在站点上，但重生成时模型手里有完整证据表，可以换一个**有据可引**的数。

### 5.5.4 「Playwright 保真度更低」是误判，真凶是**提取器**

§5.5.3 把 webmd 的命中率崩塌归给「换 Playwright 改了保真度」。**这个归因错了**，
而且错在一次实验同时动了两个变量却只看见一个：

| | 抓取器 | 提取器 |
|---|---|---|
| §5.5.2 工装 | urllib（原始 HTML） | BS4 剔 `script/style/noscript/svg`，`get_text(" ")` |
| §5.5.3 工装 = **生产链路** | Playwright（水合后 DOM） | `_parse_html`：额外剔 **`nav/footer/header/aside`**，`get_text("\n")` |

`nav/footer/header` 里正是年份、电话、地址——生产**看不到**它们，旧工装看得到。

**2×2 实测（3 个站 × 15 个 URL，每站四种组合各跑一遍）。**
关键约束：**只在两种抓取器都成功的 URL 交集上比较**——
webmd 那组 Playwright 只成功能 5/15，A/B 在 15 个上算而 C/D 在 5 个上算，
直接比是在比两组不同的页面（本轮第一版探针就犯了这个错，改成交集重算）。

| 站点 | 交集 | 提取器效应 | 抓取器效应 |
|---|---|---|---|
| www.webmd.com | 5/15 | **−10%** | +2% / +1% |
| www.teladoc.com | 15/15 | **−47%** | +1% / +2% |
| render.com | 15/15 | **−29%** | +4% / +7% |

**抓取器差异只有 +1%~+7%（Playwright 反而略多），提取器差异 −10%~−47%。**
webmd 在交集上数字命中数 A 与 C **完全相同**（5/5/4/3），B 与 D 也完全相同（3/4/2/2）
——逐条印证：**与抓取方式无关，只与提取器有关。**

**结论：「Playwright 保真度更低」不成立。** 换 Playwright 是无害的，
真正改变数字分布的是生产 `_parse_html` 比旧工装多剔了导航/页脚。

#### 这对既有结论意味着什么

- **§5.5.2 的分布高估了页面上「可定位的数字」数量**——它把导航/页脚也算进去了，
  而生产链路看不到。§5.5.2 的 42% `absent` 因此是**乐观下界**。
- **§5.5.3 第二轮（deep run）的 absent 结论更可信**：它用的是生产提取器，
  剔得更狠只会让更多数变成 `absent`——而它测出来的正好是 5/5 `absent`，
  与 §5.5.2 的 5/5 **一致**。两种口径同向，42% 站得住。
- **另一条独立事实：webmd 对浏览器路径反爬严重**——本轮 Playwright 只成功 5/15，
  而 §5.5.3 那一轮它跑出 96/160 含数字页。两次可达率差一个数量级，
  说明该站对**并发/速率**极敏感。
  → **这条同样被 §5.5.5 实测推翻：webmd 没有速率敏感性，5/15 未被复现。**

**第 2 步：不做按行业自动切表。**
理由已由 (a)(b) 给出——数据集里零金融零医疗样本，任何「按行业切表」的逻辑
在现有数据上既无法验证也无从验证。这正是 §0.1 那条原则的复述：
**不要引入无法在开放领域穷举、且失败时静默的推断。**

**预注册决策规则**（先写死，避免看到数据后自行合理化）：
某行业命中率低于全体中位数的一半、且真实运行 ≥20 次之后，才考虑为该行业整表覆盖；
在此之前**只调预算，不动表**。

**最后澄清一点**：权重表和 §0.1 里被删掉的维度表**不是同一类东西**。
维度表（`pricing_tier_v2` 落进 unknown）的失败是**静默**的，从外部完全看不出来；
权重表选错页面的失败是**可见**的——记账里直接写着它抓了哪个 URL。
所以复用权重表的代价是「命中率可能不高」，而不是「命中率不可知」。
**这正是 §5.5 该做的是先让它可观测、而不是先换掉它的原因。**

### 5.5.5 速率敏感性对照：一度判「webmd 没有速率问题」——**该结论已被 §5.6 推翻**

§5.5.4 顺手写了一句「webmd 对并发/速率极敏感」，依据只有两次可达率差一个数量级
（§5.5.4 那轮 5/15、§5.5.3 那轮 96/160）。**一次自说自话的归因，必须验证。**

设计成 2×4 因子 + 双向扫描：

| 因子 | 取值 | 为什么要有 |
|---|---|---|
| 抓取器 | urllib / Playwright | 分清「站点整体限流」与「浏览器指纹被识别」——只测后者就分不出来 |
| 并发档 | 1 / 2 / 4 / 8 | 被检验的那个变量 |
| 扫描方向 | 升序 1→8，再降序 8→1 | 若两遍趋势相反，那是**热身效应**而非速率效应 |

URL 集合固定 12 个不变，各档之间可比。webmd + teladoc 双站。

**webmd（每格 12 个 URL）**

| 档位 | 升序 PW | 降序 PW | HTTP |
|---|---|---|---|
| 1 | 12/12 | 12/12 | 12/12 |
| 2 | 12/12 | 12/12 | 12/12 |
| 4 | **11/12** | **11/12** | 12/12 |
| 8 | 12/12 | 12/12 | 12/12 |

**teladoc（对照组）**：升序与降序全部 8 格都是 12/12，HTTP 也是 12/12。

**结论：没有速率敏感性。**

1. **零趋势**：并发从 1 涨到 8，成功率不降反升，唯一例外是 C=4。
2. **升降序逐格一致** → 排除热身效应（若有限流，后扫的档位应明显更好）。
3. **HTTP 全档 100%** → 不是站点整体限流。浏览器侧也没有随并发恶化的迹象。
4. C=4 的 11/12 **两遍都落在同一格**，是**某个特定 URL 在该并发下的可复现失败**，
   不是随机抖动也不是速率——C=8（更快）反而 12/12。

**那 5/15 是什么：未复现，原因未定，不编解释。** 它与 §5.5.3 那一轮的
96/160 含数字页仍然对不上。诚实结论是**单次真实运行的可达率不可信，
必须重复测量才能引用**——而 §5.5.4 那句「反爬严重」本来就不该写。

**方法学教训（本项目第四次自造指标翻车）**
前三次错在**指标口径**；这一次错在**「两次观测不同就归因」**。
两个数据点差一个数量级时，最省事的解释永远是「有个原因」，
而那个原因往往是我们刚编出来的。**至少要有因子设计 + 双向扫描 + 对照组，
才配写「因为 X」**——本节四个格子里的结论全部来自它们，不来自直觉。

> ⚠️ **本节的「结论：没有速率敏感性」本身已被 §5.6 推翻，是设计缺陷造成的假阴性。**
> 原因写在这里而不是删掉：§5.5.5 的每档之间夹了一次 HTTP 批量，
> 那恰好给了站点恢复时间，把「背靠背持续请求」这个真正的自变量给消掉了。
> **一个「测不出效应」的设计，配上「效应不存在」这句结论，就是一个假阴性。**

### 5.6 抓取可达性加宽实测：**「Playwright 更差」对一半站成立，且失败有两种机制**

§5.5.5 的结论建立在 **2 个站 × 12 个 URL** 上。这个样本太窄，
窄到能同时得出两个方向都错的结论。加宽到 **8 站 × 30 URL × 3 遍 = 714 次观测**，
逐 URL 记录成败、**异常类型**与耗时。

| 站点 | HTTP | PW 第1遍 | 第2遍 | 第3遍 | 总体 | 3/3 稳过 | 0/3 从未过 | 时好时坏 |
|---|---|---|---|---|---|---|---|---|
| www.teladoc.com | 30/30 | 30 | 30 | 30 | **90/90** | 30 | 0 | 0 |
| render.com | 30/30 | 30 | 30 | 30 | **90/90** | 30 | 0 | 0 |
| www.figma.com | 30/30 | 30 | 30 | 30 | **90/90** | 30 | 0 | 0 |
| www.grammarly.com | 30/30 | 30 | 30 | 30 | **90/90** | 30 | 0 | 0 |
| www.brex.com | 30/30 | 27 | 25 | 23 | 75/90 | 22 | 3 | 5 |
| www.webmd.com | 30/30 | 28 | 18 | 23 | 69/90 | 16 | 1 | 13 |
| wise.com | 25/30 | 14 | 19 | 18 | 51/90 | 10 | 9 | 11 |
| www.linode.com | 28/28 | 0 | 0 | 3 | **3/84** | 0 | 25 | 3 |

总体 PW 可达率 **558/714 = 78%**，HTTP 全程正常。

#### 最重要的发现：**「失败」是两种完全不同的机制**

| 机制 | 次数 | 站点 | 失败耗时中位 | 含义 |
|---|---|---|---|---|
| `ERR_CONNECTION_CLOSED` | 43 | webmd、wise | **0.7~0.9 秒** | 服务器**主动切断 TCP 连接**。成功页要 17~20 秒，失败页 0.7 秒就断——不是慢，是被拒 |
| `TimeoutError 10000ms` | 41 | wise、brex、linode | **17~50 秒** | 页面真的在超时内没加载完，耗满了超时预算 |
| `Download is starting` | 3 | linode | — | 链接指向下载而非 HTML |

把这两类混成「Playwright 保真度低」是**第三次同源错误**：它们指向完全不同的修法
（前者要降速，后者要加超时），而且分布也不一样。

#### 回答三个悬而未决的问题

**Q1 §5.5.4 那轮 webmd 5/15 的成因？** —— **背靠背持续请求触发连接切断**。
§5.5.4 的 PW 批次紧跟在 HTTP 首页抓取之后、并发 6、中间无冷却；
§5.5.5 每档之间夹了 HTTP 批量，等于给了恢复时间，于是每格都 12/12。
本轮 webmd 三遍背靠背：28 → 18 → 23，正是被切断连接的表现。
**§5.5.5 测不出这个效应，是它自己的设计造成的，不是站点没有这个效应。**

**Q2 C=4 那个「特定失败 URL」是哪一页？** —— **不存在这样一个页面，那句话本身就是编的。**
§5.5.5 只记了总数 11/12，n=12 下 1 次失败与随机噪声不可区分，我却写成了
「某个特定 URL 的可复现失败」。本轮 n=30×3 显示：webmd 失败分散在 **14 个不同 URL**
（13 个时好时坏 + 1 个从未过），**同一个 URL 在不同遍里成功与失败交替出现**。
没有可指名的页面，因为不存在页面粒度的规律。

**Q3 更宽样本上结论还站得住吗？** —— **站不住，而且是双向错的**。
原结论「没有速率敏感性、且是 webmd 特有」。实际是：**4 个站完全没问题**
（teladoc / render / figma / grammarly 各 90/90），
**4 个站有问题，且失败机制各不相同**。原结论既漏掉了效应，又把范围划错了。

#### 一个直接的产品问题（发现但未修，等拍板）

`web_crawler._fetch_page_snapshot` 的重试循环对**所有异常一视同仁**
（`web_crawler.py:389`：只有 `attempt < attempts - 1` 就 `sleep` 后重试）。
`ERR_CONNECTION_CLOSED` 在 0.7 秒返回，**重试它等于对正在切断连接的站点加倍施压**，
且 3 次重试里每次都失败。但「快速失败就不重试」是个有代价的启发式——
临时 TCP reset 往往值得重试。**本轮不下结论、不改代码**，
要动必须先拿到「重试 vs 不重试」的对照数据。

#### 局限

- 并发固定在 6，**没有把「并发」和「持续密度」分开**——本轮只证明了
  「背靠背持续请求」有效应，不能说清是并发数还是单位时间请求数起的作用。
- 单次运行、单日、单一网络出口；不覆盖长期状态与地域差异。

#### ⚠️ 整节结论又被 §5.7 推翻：**这些数字描述的是探针，不是生产**

本节的「总体 78%」「linode 被封死」「一半站有问题」**全部是在一个生产从不使用的
负载画像下测出来的**：30 页 × 3 遍 × 并发 6 = 每站 90 次浏览器请求背靠背。
而生产对每个竞品只抓 **1 首页 + 2 内容页、串行、页间 sleep 1s**。
用生产真实调用路径 `fetch_site_profile` 重跑三个「问题站」：

| 站点 | 本节（探针 10s/并发 6） | 生产真实路径 | 耗时 |
|---|---|---|---|
| www.linode.com | 1/28 | **发现 2 / 成功 2 / 丢弃 0** | 127s |
| wise.com | 17/30 | **发现 2 / 成功 2 / 丢弃 0** | 123s |
| www.webmd.com | 23/30 | **发现 2 / 成功 2 / 丢弃 0** | 52s |

**零丢弃。** 所以「linode 浏览器路径被封死」是探针负载造出来的假象。

### 5.7 linode 根因 + 抓取链路改进方案（按证据强度排序）

§5.6 留下的两个问题：linode 的 3/84 到底怎么回事，以及重试循环怎么处理。
本节把三组对照跑完并给出方案。**方案本身尚未实施，等拍板。**

#### 三组对照，隔离出真正起作用的变量

| 参数 | linode | webmd | wise | teladoc（对照） |
|---|---|---|---|---|
| 探针：超时 10s / 并发 6 / 30 页 × 3 遍 | 1/28 | 23/30 | 17/30 | 30/30 |
| 只放宽超时 → 60s，并发 6，单遍 | **11/28** | **28/30** | **21/30** | 30/30 |
| **生产真实路径** `fetch_site_profile` | **成功 2 / 丢弃 0** | **成功 2 / 丢弃 0** | **成功 2 / 丢弃 0** | — |

**linode 没有被封。** 根因是**页面慢**：10s 预算下 81 次失败耗时中位 49.9 秒，
三次成功的耗时 25.3/26.9/26.5 秒——**刚好卡在 10s goto + 10s networkidle + 5s
的预算边界之外**。放宽到 60s 后成功率翻了 11 倍，再换成生产那种「1 首页 + 2 内容页、
串行、页间 sleep 1s」的轻负载，**零失败**。

（补充一条实测口径差异：`fetch_site_profile` 给**发现出来的内容页**传的是
`discovered_page_timeout=15` + `max_attempts=1`（`web_crawler.py:287-288`），
而首页走默认 `TIMEOUT_SECONDS=60` + `MAX_RETRIES=3`。所以「重试一视同仁」
这个问题的实际暴露面**只有首页那一次调用**，不是风暴。）

#### 改进方案（按证据强度排序，不是按「听起来对」排序）

**P1｜让失败页可见 —— 证据强度最高，且是其余一切的前提**

`web_crawler.py:291` 是 `except Exception: continue`：**失败页被静默丢弃，
不记 URL、不记原因**。本次全部结论都要靠外部探针才能取得，正是因为生产日志
对此一无所知——`refetched` 列表里只有 `status: failed`，没有任何可分类的东西。
把丢弃的 `(url, 异常类型, 耗时)` 记进 `fetch_site_profile` 的返回值即可（约 10 行）。
**没有这一条，P2~P4 的效果在生产里都无法度量。**

**P2｜`discovered_page_timeout=15` —— 实测后**不改**，前提不成立**

原判断来自 §5.6 的 714 次观测：「10s→60s 让 linode 从 1/28 变 11/28，
超时预算是主导变量，15s 只有首页 60s 的 1/4，偏小」。

**这个判断把探针画像当成了生产画像**——正是第 5 条教训本身。
用生产真实路径 `fetch_site_profile(max_pages=3)` 跑双臂对照
（每站内部 15s → 60s 交替，消除时间漂移），8 站 × 2 轮 = 32 次运行：

| 站点 | 15s 臂墙钟 | 60s 臂墙钟 | 两个 arm 的内容页 |
|---|---|---|---|
| www.webmd.com | 58.0 / 57.5s | 50.8 / 59.6s | 均 2/2 |
| www.teladoc.com | 21.5 / 25.1s | 27.3 / 25.0s | 均 2/2 |
| render.com | 53.5 / 54.8s | 55.9 / 54.4s | 均 2/2 |
| wise.com | 117.7 / 126.8s | 121.6 / 122.5s | 均 2/2 |
| www.brex.com | 53.1 / 37.5s | 50.0 / 44.6s | 均 2/2 |
| www.figma.com | 40.0 / 43.2s | 36.1 / 41.5s | 均 2/2 |
| www.grammarly.com | 50.0 / 51.6s | 48.5 / 57.6s | 均 2/2 |
| www.linode.com | 136.5s | 137.3s | 均 2/2 |

**32 次运行，两个 arm 全部 2/2、零失败，墙钟差异 ±10% 且方向不一致。**

结论：`15s` **不是**生产负载下的约束条件。生产的站内发现**已经挑中了
15 秒内能加载完的页面**——超时上限根本没被碰到，所以调大它既不多拿页面，
也不多花时间（超时是上限，不是成本：只有页面真慢时才付钱）。

**因此不改。** 「能改善也要做」的前提是「能改善」，而实测说不能。
留着的价值是：**如果将来发现某个站的内容页系统性超时，`failed_pages`
会把 URL 和耗时记下来**，那时再按证据调，而不是现在就凭 §5.6 的探针数字改。

**P3｜不重试「注定不是 HTML」 —— 结构性确定，可直接做**

`Download is starting`（linode 观察到 1 次）意味着该 URL 返回的是文件而不是页面，
重试**在定义上**不可能产出 HTML。这条不需要对照数据，是定义使然。

**P4｜`ERR_CONNECTION_CLOSED` 不重试 —— 证据齐了，判定「不做」**

§5.6 里有 43 次，但**全部来自 10s 超时的探针**。换成生产参数后重新算，
这个事件的发生率比探针画像低一个量级，而它作用的那两个调用点一旦失败
就是**整个竞品归零**，不重试的期望收益反而是负的。详见下面「P4 的证据补足
方案」——Q0 直接用已有数据回答了，Q1 由预注册规则判定为不触发。

#### P4 的证据补足方案：Q0 已答，Q1 由预注册规则判定不触发

**Q0（第一问）：在生产负载画像下，这个失败到底多频繁？** —— **用已有数据答了，零新增观测。**

| 口径 | 样本 | `ERR_CONNECTION_CLOSED` |
|---|---|---|
| 10s 高密度探针（3 遍，并发 6） | 714 | 43 = **6.0%** |
| 生产超时 60s + `max_attempts=1`，4 个最差站 URL 池，单遍 | 118 | 2 = **1.7%**（95% 上界 6.0%，全在 webmd） |
| **生产真实路径** `fetch_site_profile`（发现页 15s + `max_attempts=1`） | 64 次内容页抓取 | **0 失败** |

> 如果生产画像下它接近 0，那这个决策对产品几乎没有影响——
> **正确结论是「不动」，而不是花半小时去优化一个几乎不发生的事件。**
> 这一问比下面两问都重要。

**Q0 的答案是「接近 0」**。最后一行是决定性的：32 次生产路径运行、64 次内容页
抓取，`failed_pages`（P1 留痕）**一条都没有**。

**更要紧的是第二条事实：内容页根本不重试。** `web_crawler.py:319` 对发现出的
内容页显式传 `max_attempts=1`，所以「`ERR_CONNECTION_CLOSED` 要不要不重试」
这个问题在生产里**只作用于两个调用点**——`fetch_page_content`（`:264`）和
`fetch_site_profile` 的首页（`:290`），每个竞品每轮各 1 次。发现页那条路上，
P3 落地与否完全不可观测。

在这两个点上，不重试的代价不是「少一页」，而是**整个竞品归零**：首页抓取
没有兜底，异常直接抛出 `fetch_site_profile`。于是 1.7% 的首次失败率乘上
全损，期望收益为正；而重试最多多花 2 次请求 + 2 次退避（约 3s）。
**在这两个点上，现有重试是对的，把它关掉是拿确定的成本换不确定的收益。**

**Q1：重试的边际转化率是多少？** —— **不触发。** 原设计如下，留档说明为什么按规则不执行。

- **设计**：同一 URL 序列跑双臂。臂 A `max_attempts=1`（不重试），
  臂 B `max_attempts=3`（现状）。两臂背靠背，消除时间漂移。
- **主指标**：`P(第 k 次成功 | 第 1 次是连接切断)`，k = 2, 3。
  这是唯一能直接支撑「该不该重试」的量——不是成功率，是**边际转化率**。
- **样本量硬要求：≥30 个连接切断事件**。理由要写清楚：n=30 且观察到 0 次
  转化时，可给出「真实转化率 < 9.5%（95% 置信）」的结论；n<30 时，
  「转化率其实有 20%」这个假设排除不掉，结论就只是噪声。

**Q2：代价是多少？** —— 不必再测：单事件最多多花 2 次请求 + 2 次退避（约 3s），
而它要防的是整个竞品归零。量级已经一边倒。

**预注册决策规则（看到数据前写死，避免事后自行合理化）：**

| 条件 | 决定 | 本次 |
|---|---|---|
| Q0 显示生产画像下 ≥10% 的抓取会撞上它 **且** Q1 边际转化率 ≥30% | 保持重试（收益压倒代价） | Q0 = 1.7%，未达 |
| Q1 边际转化率 = 0 **且** n ≥ 30 | 不重试 | 未测 |
| 0 < 边际转化率 < 30% | 按 Q0 的事件频率与 Q2 的代价权衡 | 未测 |
| n < 30 | **维持现状，不改**——证据不足本身就是结论 | — |

**为什么 35 分钟的 Q1 方案也不该做**：它的样本量估算（2 站 × 30 URL × 3 遍
≈ 180 次抓取 ≈ 11 个事件）**是按探针画像 6% 的发生率算的**。生产真实发生率是
1.7%，同样规模的抓取只能凑到约 3 个事件，差预注册门槛一个数量级；要凑够 30 个
需要约 1760 次站点抓取。而且就算测出边际转化率非零，结论也只能落在
`fetch_page_content` 和首页这两个调用点上——内容页本来就不重试。
**这是第六次差点栽进同一个坑：拿探针画像的数去规划生产画像的实验。**

**留在代码里的钉子**：`tests/test_crawler_failure_reporting.py::test_connection_closed_is_still_retried`
把「暂时不处理」写成断言。下次谁想动它，得先推翻这三条实测数字。

#### 这已经是第五次自我推翻，前四次与本次的共同教训

| # | 错在哪 | 检查方法 |
|---|---|---|
| 1 | 自造 oracle 口径错 | 换可判读尺子重算 |
| 2 | 原始子串匹配 | 改用生产同款 `extract_numbers` |
| 3 | 未测假设当设计依据 | 去找仓库里已有的断言 |

### 5.8 「可补抓缺口」的定义 —— **已实施**（`refetchable_gaps`），但**接入点被实测推翻**

**指什么**：`ungrounded_claim` 的触发条件是「句中任一数字不在所引证据原文中」，
它把 `1`、`24` 这种数一并算进来。定义要回答：
**这次补抓到底有没有把缺口需要的数字带回来。**

**落地**：`src/agent/gap_refetch.py` 的 `refetchable_gaps(violations, texts)`
纯函数，返回 `{violation 下标: 该违规里可补抓的数字}`。
10 条合成用例 + 4 条真实评测夹具用例；6 组变异注入全部变红。
`mvp_workflow` 里记成 `gap_refetch_result.refetchable_gap_count`。

**两条门槛同时成立：**

| # | 门槛 | 对应的实测情形 |
|---|---|---|
| (a) | 数字**至少两位** | 个位数在任何页面都存在，定位不到具体页。实测 20 个缺失数字里 **12 个（60%）**是这种 |
| (b) | 数字出现在**当前可引用的证据原文**里 | 实测 42% 的缺口在站点上压根不存在，是模型编的数 |

(b) 的匹配**复用 `citations.extract_numbers`**，与 `verify_report` 同一套归一化——
这正是 §5.5.2 记下的那处工装坑（原始子串比对会把 `99043013` 误判成「站点上没有」）。

**口径选择：喂「证据原文」而不是「页面正文」**（接线时才发现必须想清楚）。
重生成的报告只能引用证据；一个数字连证据都没进，报告就无从把它引对。
且工作流补抓后手里只有 `extracted_data`，页面正文压根没回传
（`_fetch_single_competitor` 只返回 `raw_pages` 的 `content_length`）。

**它与 `plan_gap_refetch` 是两道独立的闸门，职责不重叠：**

```
verify_report ──→ plan_gap_refetch（该不该为这个站点抓）──→ 抓取
                                                            ↓
                                   refetchable_gaps（带回了多少缺口数字）→ 仍照常重生成
                                                            ↓
                                                   报告重生成（最贵的一步）
```

`gap_ambiguous` 夹具验证了两者独立：一句话引两家 → `plan_gap_refetch` 判
`ambiguous_target` 不抓，但那个数字本身仍可能是可补抓的。

#### ⚠️ 一度想用它拦重生成，**被现成夹具证伪**

最初的设计是「`(b)` 不成立就跳过报告重生成」，理由写成「42% 的缺口压根不存在，
再重生成模型只会再编一个」。**接进 `mvp_workflow` 时立刻被阳性对照打脸**：

`test_refetch_turns_third_draft_green` 里，缺口数字 `99` **从未出现在任何证据里**
（补抓带回的是 `79`），模型却在第三次生成时拿到新证据表、自己把数字改成 `79`，
校验转绿。也就是说 **`absent` 类缺口恰恰是重生成能修的那一类**——
生成时手里有完整证据表，模型有得选，不必接着编。

「重生成修不好 `absent`」是**从未测过的假设**，而现有夹具证明它反了。
按 §0.1 的纪律：自造指标与可判读事实冲突时先怀疑指标——**指标错了，不是代码错了**。

**现在只做观测，不做闸门**，并用
`test_gap_counter_is_observability_only_and_never_blocks` 钉死这个行为。
将来若要拿它当闸门，必须先拿出「抑制 vs 不抑制」的对照数据，并同步改掉那条用例。

**这是本项目第三次自造指标翻车**（前两次见 §5.5.1 的 oracle、§5.5.2 的子串匹配）。
三次的共同点：**指标都是我自己定的，而可判读的事实都在仓库里**——
第一次在评估脚本里，第二次在实测工装里，这次在设计判断里。检查方法也一样：
先去找仓库里已有的、别人写死的断言。

**已知边界（明确接受，不是遗漏）**：本定义只挡「压根不存在」，
**不挡「到处都是」**。像 `24` 这种在半数以上页面都出现的数仍会通过 (b)。
要区分它们需要按「出现页数」设阈值，而 `page_budget` 只有 3 页、n=12 的样本
支撑不了任何阈值——按 §0.1 的纪律，先要更多真实运行再谈阈值。

## 7. 风险与明确不做的事

**风险**

1. **第三次生成未必会正确引用新证据。** 这是整个方案的价值前提——
   模型可能被要求改却只改了措辞。→ 必须端到端测 `resolved_gap_count`，
   不能只看「抓到了页面」。
2. **成本比 v1 估的高**：补抓 = 1 次首页重抓 + ≤3 页抓取 + ≤3 次抽取 + **1 次完整报告生成**。
   报告生成是最贵的一次调用。
3. **候选页可能根本不存在**：`discover_research_links` 只认同源，且优先级词表是
   **先验**（`DEFAULT_PRIORITY_TIERS`，`web_crawler.py:34`）——
   补抓阶段沿用同一张表，命中率低是**预期结果**，不是 bug，评测要如实记录。
   （注：旧版的「零分即丢弃」已按 §0.2 修复，不再是丢弃源；当前的丢弃源只有
   `excluded_segments` 与显式 `min_score`。）
4. **legacy 无预算记账**：见 §4.4，第二层未接线前只有硬上限。

**明确不做**

- 不引入 LangGraph 或任何新框架
- 不新增第三方依赖
- 不做补抓—校验的递归循环（报告至多 3 次生成、补抓至多 1 轮）
- 不改动 M2 冻结的引用契约 `[e:id]`（tag `citations-contract-frozen`）
- 不为补抓顺手重构整个 legacy 预算体系（只做 §4.4 两层）
- 未拿到命中率数据前不调大页数上限
