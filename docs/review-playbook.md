# 评审作业手册

> 把 2026-10-15 评审复盘的四条改进固化成可复用资产。
> 状态：**手册本身即可用**（模板与 prompt 可直接粘贴）；反证执行器是阶段二，见文末。
> 配套：`docs/l2-baseline-plan.md`（取数规程）、`.self-improving/lessons.md`（本机教训库）。

## 为什么现有多方交叉评审不够用

「多个智能体各出一份意见、我汇总」的失效模式不是「意见不够多」，是**意见相关**。

子智能体拿到的是主智能体裁剪过的问题描述和主智能体选好的证据，它们会收敛到同一个
框架里。而 2026-10-15 那次评审的 7 次自我推翻里，**5 次是框架错**——交叉评审在这种
情况下只会让错误更一致、更自信，不会让它更少。

所以手册要做的不是「增加评审者」，是把每个评审者的**输入边界**和**输出格式**固定死，
让相关性无处藏。

## 1. 评审契约模板

送评审之前先把下面四栏填完。**填不出来就不要送评审**——填不出来本身就是结论：
这件事现在无法被证伪。

```
## 送审材料
- 方案/结论文档路径：
- 相关代码路径：
- 支撑数据路径：
- 明确不送审的内容（以及为什么）：

## 每个评审者只准看什么
- A（代码对账）：代码 + 测试 + 方案文档。不看数据。
- B（数据推论）：数据 + 方案文档 + 取数规程（manifest）。不看代码。
- C（反驳）：方案文档 + 「本方案可能在哪失败」三问。**不给结论，不给理由。**

## 必须输出的节
1. 结论（每条标注：支持 / 不支持 / 无法判断）
2. **无法验证的断言**（见 §4）
3. 触发的反证清单命中项（见 §6）

## 判定标准
- A 报「不支持」的条目：方案必须改，或明确写「已知错误，暂不改，理由是…」
- B 报「数据推不出」的条目：补数据，或降级该结论的措辞强度
- C 报出致命失败模式：该方案不进入实施，直到被处理
```

## 2. 三个角色 prompt（可直接粘贴）

### 角色 A：代码对账

```
你的任务只有一件事：把这份方案里的每一条「已经实现 / 已经如此」的主张，
逐条和仓库里的实际代码对账。

规则：
- 逐条输出三选一：支持 / 不支持 / 无法判断。不允许输出「看起来合理」。
- 「支持」必须给出 file_path:line_number 作为证据；给不出就不是支持。
- 不评价设计好坏，不猜测意图，只对账。
- 不要读数据文件，也不要读方案里给出的理由——理由会带偏你。

末尾必须输出：
【无法验证的断言】
- 方案里哪些说法你只是接受了、没有独立核对过代码？逐条列出。
```

### 角色 B：数据推论

```
你的任务只有一件事：判断这份方案的每条结论，能不能从给定的数据里推出来。

规则：
- 逐条输出：能推出 / 推不出（缺什么）。不允许输出「数据基本支持」。
- 先核对取数规程（manifest / 负载画像 / 采集时间窗），再核数字。
  数字本身再精确，如果规程不可比，结论就是「推不出」。
- 重点检查：结论依赖的前提有没有被单独验证过？还是被顺带假设了？
- 不读代码，只看数据与方案文档。

末尾必须输出：
【无法验证的断言】
- 哪些说法你无法用现有数据判定？逐条列出。
```

### 角色 C：反驳

```
你的任务是**推翻**这份方案。你没有别的职责。
不给结论、不给理由，只给方案本身。

先回答三问，每问都要给出「最坏情况下会发生什么」：
1. 这个方案依赖哪个前提？如果这个前提是错的，方案会怎样？
2. 这个方案在什么输入/时序/负载下会失效？举个具体场景。
3. 有没有更简单的做法能拿到同样的效果，而不需要这套复杂度？

规则：
- 你的默认立场是「这个方案会被推翻」，找不到反驳点不算通过，
  要写清「我试过哪几条攻击路径，都没打中」。
- 构造不出失败场景时，明确写「我构造不出来」，不要编一个。

末尾必须输出：
【无法验证的断言】
- 哪些说法你无法证伪（只能表达怀疑）？逐条列出。
```

## 3. 「无法验证的断言」为什么是强制项

这是整份手册里性价比最高的一条。

人和 agent 在被要求「给出结论」时，倾向于把**接受的**和**验证过的**混在一起输出。
分开列的成本极低（三行），收益是立刻能看到「7 条结论里有 4 条没有独立证据」。

没有这一栏，评审就退化成了「听起来有道理」的加总——而 2026-10-15 的 P2/P4 结论
当时正是这么通过的：数字漂亮、解释自洽、**全是探针画像**。

---

## 4. 不喂结论和理由

把方案送给评审者时，**只给方案，不给「我认为这是对的」以及我的理由链**。

理由会带偏：评审者会顺着理由找补，把注意力花在「理由是否自洽」而不是
「结论是否成立」。2026-10-15 那次多个 agent 意见高度一致，根因就在这里——
它们全部继承了我的框架。

真要交代背景，把背景写成**中立的事实陈述**，不要写成论证。

---

## 5. 反证清单：评审替代不了的三样东西

2026-10-15 真正推翻我的不是任何一个评审智能体，是三个机械手段。
按性价比排序，加评审者的边际收益低于加反证手段的边际收益。

| # | 手段 | 判定问题 | 不过怎么办 |
|---|---|---|---|
| 1 | **变异测试** | 把守卫逻辑改坏，相关测试**真的会红吗**？ | 没红 = 守卫是装饰，删掉 |
| 2 | **仓库现成夹具** | 仓库里有没有现成的测试/夹具能**直接证伪**这个设计？ | 有 → 设计推翻，重来 |
| 3 | **走生产入口实测** | 这个结论是走生产入口跑出来的，还是外部脚本跑出来的？ | 外部脚本 → 结论降级为「待验」 |

第 2 条是那次最便宜的推翻：`test_refetch_turns_third_draft_green` 里模型自己把
99 换成 79，直接证伪了「缺口数字不在证据里就跳过重生成」。**动手设计之前先去找，
不要设计完再找证据。**

## 6. 一个已填实例（评审契约，P4）

**这是事后重构，用来验证模板填得通，不是真跑过的三方评审**，因此它只能证明
「模板可用」，不能证明「这套流程能提高发现率」。下面三条判定都是我从自己的
纠错记录里回填的。

拿 2026-10-15 的 P4 走一遍：

```
## 送审材料
- 方案：docs/implementation-draft-gap-refetch-2026-10.md §5.7 P4
- 代码：src/crawler/web_crawler.py
- 数据：%TEMP%\ra-scratch\prodparams.json、wallclock.json、availability.json
- 不送审：改动本身只收 Download is starting，不收 ERR_CONNECTION_CLOSED

## 各评审者只看
- A：web_crawler.py + tests/test_crawler_failure_reporting.py + §5.7 P4
- B：三份 json + §5.7 P4 + 取数规程（manifest 尚不存在 → 这本身就是一条命中）
- C：只有 §5.7 的 Q0 那一段

## 判定结果
- A：报「不支持」——P3 对内容页不可观测（内容页传 max_attempts=1，本就不重试）。
  这条推翻了「P3 覆盖了发现页」的隐含说法。
- B：报「推不出」——三份数据的负载画像互不相同，不能直接相减。
  但按生产路径口径（wallclock.json，64 次内容页抓取 0 失败）足以支撑 Q0 < 10%。
- C：构造出致命场景——「如果首页抓取也走 max_attempts=1，整个竞品直接归零」，
  说明 P4 的适用面判断错了。
```

三条判定各报一条，其中两条直接改变了结论。**这就是这套模板存在的理由**：
不是多几个人看，是让每个人只能看到自己该看的那一半。

**首次真跑时必须记录**：三方是否给出独立于我判断的发现、有没有重复结论、
「无法验证的断言」栏实际列出了几条。否则这套流程的收益仍然没有证据。

## 7. 反证执行器（阶段二，未实施）

把 §6 的三问里能机械化的部分做成脚本，输入是改动文件列表，输出是：

1. 覆盖这些文件的现有测试（`pytest --collect-only -q <file>`）
2. 仓库里可能证伪当前设计的现成夹具（按关键词反查 `tests/`、`evals/cases/`）
3. 一份待人工填写的反证清单骨架

**刻意不自动化判定**——只负责「把该看的东西摆到面前」，判断仍然是人/agent 的活。
自动化判定听起来更强，但会退化成又一个「看起来有数字就通过」的黑盒。
