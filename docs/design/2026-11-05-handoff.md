## 1. 这套改造解决的原始问题

不是功能清单。每条对应一次真实失败或评审原文。

| # | 原始问题（真实失败 / 评审原文） | 现在的处理 | 不处理的后果 | 证据 |
|---|---|---|---|---|
| 1 | 进程重启后，内存里的任务没了，`GET /research/tasks/{id}` 对历史任务恒 404 | 读取时内存优先、SQLite 回填只读视图（`_load_task_for_read`）；事件只从 SQLite 按 `seq` 分页 | 前端刷新一次就丢任务；审计无法复盘 | `test_sqlite_read_fallback_after_restart`；track「重启后历史任务可查」 |
| 2 | 评审 3.5：「没有取消端点」；用户只能等 180s+ 长任务跑完，运维只能杀进程 | `POST /research/tasks/{id}/cancel`；取消是单调终态；工作流在写外部产物前检查取消信号 | 无法止损；杀进程会留下 running 脏行 | `LIFECYCLE_CANCEL` 相关单测；track B2 |
| 3 | 评审 3.5：`src/` 未检索到 `resume`/`checkpoint`；崩溃后任务永久停在 running | 六阶段检查点落 SQLite；`/resume` 手动续跑；可选启动自动恢复 | 失败任务无法续跑，重复烧 token；只能人工重跑 | 离线强杀探针 10/10；真服务重启 1/1 |

## 2. 开关全清单

所有开关都是**环境变量**，进程启动时读取。`0` 即关闭（除非另注）。

| 变量 | 默认 | 作用 | 什么时候该开 / 关 | 开着的代价 |
|---|---|---|---|---|
| `LIFECYCLE_STAGE_EVENTS` | `1` | 六阶段 `stage_start` / `stage_end` 事件 + 阶段 attempt | 默认开。排障需要阶段耗时与失败阶段时必须开 | 每任务多约 12 行 `task_events`；不影响任务结果 |
| `LIFECYCLE_CHECKPOINTS` | `1` | 每阶段成功后写 `task_checkpoints` | 默认开。只要用 `/resume` 或启动恢复就必须开 | 每任务约 6 行；检查点不含凭据，所以鉴权站点恢复必失败 |
| `LIFECYCLE_CANCEL` | `1` | 工作流在写外部产物前检查取消信号 | 默认开。要求「取消后绝不再写报告」时必须开 | 代码路径多几个检查点，成本可忽略；关掉后 asyncio 取消仍会终止任务，但取消与同步写盘之间的窗口变宽 |
| `LIFECYCLE_ATOMIC_REPORT` | `1` | 报告按 task 固定文件名 + `.tmp` + `os.replace` | 默认开。只要在乎「磁盘文件数 = 台账行数」就必须开 | 同一任务重跑会覆盖旧报告（这是目的）；关掉回到时间戳命名 |
| `LIFECYCLE_REPORT_DRAFT` | `1` | 报告正文草稿按 task 落库，重跑复用 | 默认开。报告阶段贵（LLM）时收益最大 | 每任务多 1 份草稿（约 8 KiB）；矩阵推导与机器附录仍会重跑/重渲染 |
| `LIFECYCLE_PAGE_CACHE` | `1` | 无凭据站点页快照按 task 落库 | 默认开。抓取慢/易限流时收益最大 | 最大的新增磁盘占用（30 页约 180 KiB/任务）；只省网络，不省抽取 LLM |
| `LIFECYCLE_RECOVER_ON_STARTUP` | `0` | 启动时扫描 SQLite `running` 行并自动续跑 | **仅生产单实例**显式置 `1`。开发/测试、多副本、刚恢复备份时必须 `0` | 重启风暴；未完成阶段重跑；鉴权站点必失败；重复计费 |
| `LIFECYCLE_RECOVER_CONCURRENCY` | `2` | 自动恢复同时执行的任务数上限 | 单实例生产建议保持 2，按下游配额调整 | 调大可能触发站点/LLM 限流；调小恢复慢 |
| `UNIT_FETCH_TIMEOUT` | `240` | 单站抓取超时（秒） | 目标站慢时上调；有强 SLA 时下调 | 太小把慢站判失败；太大批次被拖住 |
| `CACHE_PRUNE_ENABLED` | `1` | **只控制启动钩子**是否执行清理 | 排障冻结现场时置 `0` | 关掉后启动钩子不清理；CLI `--apply` 仍会删（见坑 8） |
| `CACHE_PRUNE_ON_STARTUP` | `0` | 启动时执行一次真实清理 | 单实例、数据量大时用；否则用 CLI/定时任务 | 每次重启都写库；参数配错会一次性淘汰大量终态缓存 |
| `CACHE_COMPLETED_KEEP_DAYS` | `7` | completed/cancelled/partial 的缓存保留天数 | 需要「完成后再看」更久时上调 | 越大占用越多；超过容量上界会被提前淘汰，实际保留可能短于该值 |
| `CACHE_FAILED_KEEP_DAYS` | `30` | failed 的缓存保留天数 | 复盘窗口长时上调 | 失败任务通常积压，调太大会顶满容量 |
| `CACHE_MAX_ROWS` | `300000` | `page_cache` + `task_drafts` 全局行数上界 | 按部署任务量调整 | 调太小会静默淘汰终态缓存（不删报告/事件） |
| `CACHE_MAX_BYTES` | `2147483648` | 全局数据字节上界（2 GiB） | 同上；按磁盘余量调整 | 只计 BLOB 长度，实际磁盘约 1.2–2 倍 |
| `STARTUP_CONFIG_CHECKS_ENABLED` | `1` | 启动配置自检总开关 | 默认开。排障时可临时置 `0` 跳过全部矛盾检查 | 关掉后矛盾配置会照常启动，后果由部署方承担 |
| `AGENT_CONTEXT_FOLD_TOKENS` | `24000` | 历史 token 超过该值触发折叠；低于该值的预算不注册 `read_evidence` | ReAct 长任务需要时保留默认；不想折叠可调到远大于预算 | 折叠会摘要旧消息，原文只能按证据指针回读 |
| `AGENT_CONTEXT_FOLD_KEEP_RECENT` | `4` | 折叠时保留最近消息条数 | 需要模型记住更多近期步骤时上调 | 保留越多，折叠收益越小 |
| `AGENT_CONTEXT_FOLD_MIN_CHARS` | `200` | 小于该长度的工具观察不折叠 | 默认即可 | 调太小会把短观察也摘要，增加噪声 |
| `AGENT_UNREAD_EVIDENCE_WARN_THRESHOLD` | `1` | 被折叠但未回读、且被终答引用的证据条数达到该值时打 warning；`0` 只计数不告警 | 真实 LLM 上线初期保持 `1`；噪声大时先看 `unread_cited_evidence` 再决定是否调高 | 只影响日志告警，不增加 token、不阻断任务 |

相关但**不属于**本改造新增的部署开关：`TASK_STORE_BACKEND`（默认 `memory`）、`DATABASE_PATH`、`AGENT_MODE`。它们会改变恢复/历史读取的前提，见第 6 节。

`CACHE_PRUNE_ENABLED` 的实际作用域只有启动钩子：置 `0` 只会跳过启动清理，**不会**阻止 `python -m src.storage.prune --apply` 删数据。

### 高危配置（最容易配错的三个）

1. **多副本/多 worker 下把 `LIFECYCLE_RECOVER_ON_STARTUP` 置 `1`**：同一 SQLite 的每个进程都会扫描同一批 `running` 行，重复抓取、重复计费、重复写报告。当前没有租约，**只能单实例**。
2. **`CACHE_PRUNE_ON_STARTUP=1` + 把 `CACHE_MAX_ROWS` / `CACHE_MAX_BYTES` 调得很小**：会在启动时静默淘汰终态任务的缓存。报告、事件、检查点不丢，但复盘用的原始页与草稿会丢；结果里只有 `caps.exceeded_after` 能看出来。
3. **关掉 `LIFECYCLE_CHECKPOINTS` 却保留 `LIFECYCLE_RECOVER_ON_STARTUP=1`**：新任务不再有检查点，崩溃后启动恢复找不到证据，会把残留 `running` 行直接标成 `failed`（`reason_code=no_checkpoint`）。看起来只是「关掉一个功能」，实际把自动恢复变成了自动判死。

### 启动配置自检（fail-fast）

启动钩子在任何副作用之前调用 `validate_startup_config()`。矛盾组合直接抛 `StartupConfigError`，日志打印变量名与修法，进程不启动；总开关 `STARTUP_CONFIG_CHECKS_ENABLED=0` 可跳过全部检查（仅排障用）。

| 规则 | 行为 | 提示里必须有的内容 |
|---|---|---|
| `LIFECYCLE_RECOVER_ON_STARTUP=1` + `LIFECYCLE_CHECKPOINTS=0` | 拒绝启动 | 两个变量名、`no_checkpoint` 后果、二选一修法 |
| `LIFECYCLE_RECOVER_ON_STARTUP=1` + `WEB_CONCURRENCY` / `UVICORN_WORKERS` / `APP_WORKERS` / `LIFECYCLE_RECOVER_REPLICAS` 任一 `>1` | 拒绝启动 | 具体变量名、无租约的重复恢复后果、关闭恢复的修法 |
| `LIFECYCLE_RECOVER_ON_STARTUP=1` 且上述变量都未设置 | 告警，不拒绝 | 原文「无法探测副本数/worker 数……责任在部署方」 |
| `CACHE_PRUNE_ON_STARTUP=1`（且 `CACHE_PRUNE_ENABLED=1`）+ `CACHE_MAX_ROWS<1000` 或 `CACHE_MAX_BYTES<100 MiB` | 拒绝启动 | 变量名、下限值、调大或关闭启动清理的修法 |

默认配置全部通过；检查只读环境变量，不改变任何默认值语义。自检只在 FastAPI 启动钩子里执行，直接调用工作流或 CLI 不会触发。

## 3. 怎么回滚

原则：**所有新表都是 `CREATE TABLE IF NOT EXISTS`，没有破坏性迁移**。关开关只停行为，不删已有数据；不需要迁移回退。

| 关掉的项 | 系统退化成什么 | 会丢数据吗 | 要迁移回退吗 |
|---|---|---|---|
| `LIFECYCLE_STAGE_EVENTS=0` | 不再有 `stage_start`/`stage_end`，只剩任务级/业务事件 | 不丢；已有事件行保留 | 否 |
| `LIFECYCLE_CHECKPOINTS=0` | 新任务不再落检查点，`/resume` 与自动恢复对新任务不可用 | 不丢；旧检查点保留（但可能过期，续跑会重放旧阶段） | 否 |
| `LIFECYCLE_CANCEL=0` | 外部 `running.cancel()` 仍会终止任务并落 `cancelled`；但「写产物前检查」消失，取消与同步写盘之间可能仍写出一份产物 | 可能多一份取消后的产物 | 否 |
| `LIFECYCLE_ATOMIC_REPORT=0` | 回到时间戳命名 + 直接写；崩溃窗口重新可能出现 1 台账 / 2 文件 | 不丢；旧固定名文件保留 | 否 |
| `LIFECYCLE_REPORT_DRAFT=0` | 每次进报告阶段都重新调 LLM；已有草稿保留在库中，再打开时会被复用 | 不丢 | 否 |
| `LIFECYCLE_PAGE_CACHE=0` | 不再读写页缓存；重跑整段重抓；已有缓存行保留，可被清理或再启用 | 不丢 | 否 |
| `LIFECYCLE_RECOVER_ON_STARTUP=0` | 重启后 `running` 行不自动跑；仍需人工 `POST /resume` | 不丢，但任务会停在 running | 否 |
| `CACHE_PRUNE_ENABLED=0` | 启动钩子不清理；CLI 仍可显式 `--apply` | 不丢（本来只删缓存） | 否 |
| `CACHE_PRUNE_ON_STARTUP=0` | 不在启动时清理；改用 CLI/定时任务 | 不丢 | 否 |
| 把保留天数调到极大 | 年龄清理基本不生效，只剩容量上界淘汰 | 不丢 | 否 |
| 把 `CACHE_MAX_ROWS` / `CACHE_MAX_BYTES` 调到 `0` | 下一次清理会淘汰所有**终态**缓存；running 仍保留，`exceeded_after=true` | 缓存页/草稿丢失；报告、事件、检查点不丢 | 否 |

整体回退到改造前的最快方式：

```powershell
$env:LIFECYCLE_STAGE_EVENTS=0
$env:LIFECYCLE_CHECKPOINTS=0
$env:LIFECYCLE_CANCEL=0
$env:LIFECYCLE_ATOMIC_REPORT=0
$env:LIFECYCLE_REPORT_DRAFT=0
$env:LIFECYCLE_PAGE_CACHE=0
$env:LIFECYCLE_RECOVER_ON_STARTUP=0
$env:CACHE_PRUNE_ENABLED=0
```

注意两点：

- A1–A3 的契约字段是**加法**，关不掉也不需要关；旧调用方按原字段读仍可用。
- P3 没有布尔开关，把 `AGENT_CONTEXT_FOLD_TOKENS` 调到远大于实际预算即可等效停用。
- 若要彻底清掉新表，按 `page_cache` → `task_drafts` 顺序 `DROP TABLE`；**不要**动 `task_events` / `task_checkpoints`，否则崩溃审计与续跑证据一起没了。删表前先备份 `DATABASE_PATH`。

## 4. 刻意不做的清单

| 不做 | 理由 | 什么条件下才重新考虑 |
|---|---|---|
| 多副本租约 / leader 选举 | 当前栈没有共享协调组件；引入 Redis/etcd/K8s Lease 都是新依赖。租约只包住现有恢复循环，不改变任务语义。设计结论已写死为「DB 条件 UPDATE 抢占」，见 [lease-design](2026-11-04-lease-design.md) | 要跑 `uvicorn --workers>1` 或 K8s 多副本，且数据库对所有副本真实共享、时钟可信、WAL + 短事务可接受 |
| 通用任务队列 / 工作流引擎 | 六阶段是确定性流水线，不是 DAG 编排；引入队列会把「进程内后台任务 + SQLite 检查点」换成另一套生命周期，收益不抵复杂度 | 出现跨机器的任务分片、优先级队列、延迟重试等真实需求 |
| 插件内核 / 递归分解 / 子会话 | 6 个静态工具、单用途批处理；评审 5.6 明确列为「补了也白补」 | 工具数量与并行研究单元显著增长 |
| 鉴权站点续跑 | 凭据不落盘是既有安全边界；恢复后登录态无法重建。放松边界换取续跑成功率不可接受 | 有独立的凭据托管/短期令牌方案，且通过安全评审 |
| 逐工具人工审批 | 全部工具只读，风险边界已由 SSRF/白名单/租户隔离覆盖；审批只增加延迟 | 出现真实写操作工具 |
| skills / 记忆 / 延迟工具发现 | 工具少、配置面大于收益 | 工具集与场景明显扩展 |
| 把 LLM 评审放进 pre-commit 阻断位 | 阻断位只跑确定性检查，LLM 意见只做参考（项目规则） | 不重新考虑 |

## 5. 已知边界与坑（实测踩过的）

1. **页缓存只覆盖无凭据站点**。`auth_credentials` 或 `login_url` 任一存在就不缓存；恢复后鉴权站点必失败，这是安全边界，不是 bug。
2. **清理只删 `page_cache` / `task_drafts`**。`task_events` / `task_checkpoints` / `tasks` / `reports` 一行不动，续跑证据完整。
3. **清理只认 `tasks` 表里存在的任务行**。任务行被删后留下的孤儿缓存行**永远不会被清理**；需要时手工按 `task_id` 删。
4. **running / pending 与无任务行的缓存永不清理**。如果 running 数据本身超过上界，`caps.exceeded_after=true`，不会为了满足上限去误删 running。
5. **字节口径是数据列 BLOB 长度**，不含 SQLite 页开销与索引；实际磁盘占用约为其 1.2–2 倍。容量上界不能当磁盘配额用。
6. **年龄按 `tasks.updated_at` 算，不是缓存行自己的 `created_at`**。终态时刻才起算；如果手工改过 `tasks.updated_at`，保留窗口会跟着变。
7. **`sqlite3` 的 upsert rowcount 不可靠**。`ON CONFLICT DO UPDATE` 与 `executemany` 下 `cursor.rowcount` 经常是 0（或只计部分），不能拿它判断「是否写入/更新成功」。`save_task_draft` / `save_page_cache` 返回 `True` 只代表「执行无异常」，不保证发生了新插入。需要精确判断时用 `changes()` 或回读。
8. **`CACHE_PRUNE_ENABLED` 只拦启动钩子**。`python -m src.storage.prune --apply` 不读这个变量，显式 `--apply` 一定会删。排障冻结现场时不要只设 `CACHE_PRUNE_ENABLED=0` 又手工跑 `--apply`。
9. **`LIFECYCLE_ATOMIC_REPORT=0` + `LIFECYCLE_REPORT_DRAFT=1` 是坏组合**：正文复用草稿（不花 LLM），但文件名回到时间戳，续跑仍每跑一次多一个文件。要么两个都开，要么接受重复产物。
10. **报告草稿只复用正文**。矩阵推导与机器附录仍按确定性逻辑重跑/重渲染；所以「LLM 2 → 1」不是「阶段耗时减半」。
11. **页缓存 key 是 `URL|max_pages|tiers`，不含 `custom_selectors`**。同一任务对同一 URL 先用选择器 A、后用选择器 B 重抓，会命中 A 的快照。内容哈希只校验快照自身未被改坏，不校验「与当前请求参数一致」。
12. **页缓存存的是清洗前的原始 profile**；复用时仍会重新跑 `sanitize` 与注入扫描。不要因为「缓存了」就跳过安全处理。
13. **文件名映射先于正文落库**。库不可用时退回时间戳命名（仍然同秒不同任务不撞车），但崩溃窗口的重复文件风险会回来。
14. **`os.replace` 只在同一卷内原子**。`.tmp` 与目标文件同目录；如果进程在写完 `.tmp`、尚未 replace 时被杀，`output/` 会留下 `.tmp` 孤儿文件，不会被计入报告数，也没有自动清理。
15. **检查点只在阶段成功后落盘**。阶段内崩溃会整段重跑；页缓存/草稿只降低重跑成本，不能消除重跑。
16. **恢复重建请求固定 `enable_search=True`**（见 `_task_request_from_checkpoint`）。原任务若关闭搜索，续跑会多跑一次搜索；检查点 payload 没有保存该字段。
17. **事件 `seq` 是同一数据库内全局单调，不是任务内单调**；前端断线补齐用 `after_seq`，不要用 `created_at` 排序（秒级精度会重复）。`event-log` 的 `limit` 上限 500。
18. **启动恢复默认关闭**。开发/测试尤其 `TestClient` 启动时若打开，会无条件触发真实网络抓取；见 [ADR-001](2026-11-04-adr-startup-recovery.md)。
19. **启动缓存清理失败只告警、不重试、不阻断启动**；需要确认时看日志 `启动缓存清理: ...` 或手工 CLI dry-run。
20. **多副本恢复、鉴权站点续跑、改造前同口径评测**是三项明确的未实测/未覆盖边界，见 track「未实测 / 已知边界」。
21. **启动配置自检只在 FastAPI 启动钩子里执行**。直接用脚本调 `MvpWorkflow`、`python -m src.storage.prune` 或其他非 FastAPI 入口不会触发；这些入口需要自己调 `validate_startup_config()`。
22. **副本数无法可靠探测**。自检只看显式环境变量；用 `uvicorn --workers 4` 但不设 `WEB_CONCURRENCY` 时只会告警“无法探测、责任在部署方”，不会拒绝启动。这是刻意的：探测不到就明说，不假装通过。
