### 真服务重启自动恢复（2026-11-04 实测）

目的：验证 `LIFECYCLE_RECOVER_ON_STARTUP=1` 下，进程被强杀后重启能**自动**从检查点续跑到 completed（不是手动 `/resume`）。

启动参数（两个进程相同）：

```
LLM_PROVIDER=fake
LLM_FAKE_SCRIPT=<temp>/llm_fake.json
ALLOW_PRIVATE_NETWORK_URLS=true
LIFECYCLE_RECOVER_ON_STARTUP=1
LIFECYCLE_STAGE_EVENTS=1
LIFECYCLE_CHECKPOINTS=1
LIFECYCLE_CANCEL=1
DATABASE_PATH=<temp>/reports.db
RATE_LIMIT_ENABLED=false
API_AUTH_TOKEN=ra-restart-test
APP_HOST=127.0.0.1  APP_PORT=18181
```

命令与步骤：

1. `uv run uvicorn server:app --host 127.0.0.1 --port 18181 --log-level warning`（首次启动）
2. 本地静态站（127.0.0.1:18180，每页延迟 0.5s）作为唯一抓取源；`POST /research/tasks`，`enable_search=false`
3. 跑 20s（约中段）→ `taskkill /PID <pid> /T /F`（Windows 等价强杀，含子进程）
4. 同参数重启 → 启动钩子扫描 SQLite `tasks` 的 running 行 → 自动 `_schedule_resume`
5. 轮询 `GET /research/tasks/{id}` 至终态

实测结果：

| 观测点 | 实测值 |
|---|---|
| 杀进程时点 | 20.001s |
| 杀前最新检查点 | `seq=1, stage=decompose` |
| 杀后 SQLite `tasks.status` | `running`（确认是未终态，可被恢复） |
| 重启后自动恢复事件 | `task_resumed` seq=8（payload `checkpoint_seq=1`；由启动钩子自动触发，未调用 `/resume`） |
| 恢复耗时 | 49.889s（真实重跑 crawl→citation，不是空转） |
| 最终任务状态 | `completed` |
| 最终 SQLite `tasks.status` | `completed` |
| 检查点序列 | `decompose → decompose → crawl → extract → verify → report → citation → completed` |
| stage_end 事件序列 | `decompose → crawl → extract → verify → report → citation`（跨进程读自 SQLite `task_events`） |
| 报告产物 | `output/research_report_20261104_230429_c18bbb6d.md`，含 `$49/席位/月` |

本次验证顺带修掉两个真实缺陷（不修则“重启恢复”只会得到假 completed）：

1. `server.py::on_event` 曾按 `event.status == "completed"` 一刀切改任务终态；而 stage_end / artifact_ready / crawl_complete 的 status 也是 `completed`（语义是“该阶段完成”）。结果 decompose 一结束任务就被标 completed，后续 running 事件被终态单调保护拒绝——任务在内存里永远完成、在 SQLite 里永远 running。现改为只认任务级终态事件（`completed` / `partial` / `task_cancelled` / `error`）。
2. SQLite `task_events` 建了表但运行时从未写入（只有测试写过），导致 `/event-log` 恒为空、崩溃审计不可用。现 `on_event` 同步 append 一条；写失败只记 debug，不影响任务。

### 多任务并发恢复压测（2026-11-04 实测）

目的：同一 SQLite 造 10 个 running 任务，强杀后重启，验证去重、并发上限、已完成不重跑、失败隔离。

启动参数：在上一节基础上增加 `LIFECYCLE_RECOVER_CONCURRENCY=2`；`TASK_STORE_BACKEND=memory`；
本地静态站每页延迟 0.5s。19:26 起错峰创建 10 个任务（间隔 2s），全部落检查点后 `taskkill /T /F`，
确认端口死亡且 10 行仍为 `running`，再同参数重启。

| 观测点 | 实测值 |
|---|---|
| 杀前 running 任务 | 10/10（检查点 seq 8–17，阶段均为 `decompose`） |
| 恢复总耗时（重启健康检查→全部终态） | **247.338s** |
| 恢复成功率 | **10/10 terminal=completed，1.0** |
| 重复执行计数 | **0**（每任务 `automatic=true` 的 `task_resumed` 恰 1 条；重复报告行 0） |
| 恢复并发峰值 | **2**（日志 `active=` 峰值；与 `LIFECYCLE_RECOVER_CONCURRENCY=2` 一致） |
| 已完成任务（杀前 completed） | 重启后仍 `completed`；`automatic` 恢复事件 0；447 个既有报告文件 mtime 全部未变 |
| 失败隔离 | 注入 2 个坏行：无检查点 → `failed` + `reason_code=no_checkpoint`；检查点缺请求字段 → `failed` + `request_rebuild_failed`；其余 10 个照常完成 |
| 失败可定位 | 日志两行 `ERROR:server:任务 bad-... 恢复失败 [reason_code]`；SQLite `task_events` 各一条 `error` 事件 |
| 恢复汇总日志 | `启动恢复完成：候选 12，已调度 10，失败 2，跳过 0，并发上限 2` |

补充：为覆盖"不同检查点位置"，用一次真实完成任务的检查点快照把 10 个 running 行种在
`decompose/crawl/extract/verify/report/citation`（1/1/2/2/2/2），再次重启：
**10/10 completed，耗时 51.714s，并发峰值 2，重复恢复 0**。从 `report`/`citation` 起步的任务
没有新写报告行（`reports_rows=0`），证明恢复不会重放已完成的产物写入。

本轮顺带修掉三个真实缺陷：

1. 取消端点调用 `store.add_event(event)` 少了 `task_id` 参数，`POST .../cancel` 必 500；改为
   `add_event(task_id, event)` 并同步写 SQLite（否则 `/event-log` 看不到取消）。
2. 自动恢复事件只写内存 store，没进 SQLite `task_events`，导致重启后无法统计"被恢复几次"；
   现 `_recover_running_tasks` 落库后再调度。
3. 手动 `/resume` 同样有 `add_event` 参数错误且事件不落库；一并修复并补 `automatic=false`。

事件字段与真实序列见 [2026-11-04-lifecycle-events-contract.md](2026-11-04-lifecycle-events-contract.md)；
启动恢复默认值决策见 [2026-11-04-adr-startup-recovery.md](2026-11-04-adr-startup-recovery.md)。

| `/event-log` 分页 | 9 页 × 3 条 + 1 页 × 1 条 + 1 页空：`seq 1..25`，**严格递增、重复 0、可 drain 到空页** |
| 断线补齐 | `after_seq=24` 返回 seq 25；`after_seq=25` 返回空，边界不含重复 |
| 内存优先 | 重启后新建任务，直接把 SQLite 改成 `failed`，API 仍返回 `running`（且带实时 `events`），未回退到 SQLite 视图 |

回归测试：`tests/test_lifecycle_v2.py::test_sqlite_read_fallback_after_restart`（SQLite 回填命中、
`from_sqlite=True`；内存命中时即使 SQLite 为 `failed` 仍返回内存 `running`）。

### 阶段内崩溃重跑成本（离线探针，2026-11-04 实测）

中断位置：阶段工作已完成、检查点尚未落盘（最坏窗口）；citation 额外测了
“报告文件已写、`task_status` 尚未落库”窗口。每次外部调用注入 0.3s 延迟，
使重复调用的耗时可见（生产耗时 ≈ 调用次数 × 真实单位耗时）。

| 阶段 | 基线阶段耗时 | 重跑阶段耗时 | 额外抓取 | 额外 LLM 调用 | 重复产物 |
|---|---|---|---|---|---|
| decompose | 0.312s | **0.308s** | 0 | **1** | 0 |
| crawl | 1.648s | **1.639s** | **1 次完整抓取** | 0（本夹具） | 0 |
| extract | 0.000s | 0.000s | 0 | 0（夹具预置抽取结果） | 0 |
| verify | 0.001s | 0.001s | 0 | 0 | 0 |
| report | 0.617s | **0.615s** | 0 | **2** | 0 |
| citation（写盘后） | 0.003s | 0.004s | 0 | 0 | **1 个重复报告文件**（崩溃时已 1 个，续跑后 2 个；DB `reports` 行仍 1） |

结论：

- **代价最高的是 crawl 与 report**：crawl 重跑等于整段重新抓取（网络/限流/时间），
  report 重跑等于 2 次报告 LLM 调用（token 计费与延迟）；decompose 也要重放 1 次 LLM。
- **必须做断点的只有三处**：crawl 的页级缓存、report 的草稿落盘、citation 后写盘幂等。
  三处均已实施，实测收益见下节；其余阶段重跑成本可忽略，不为它们引入队列或插件。
- 该探针的 extract 阶段在本夹具无外部调用；生产若抽取走 LLM，应按“抽取调用数”同比例计入，
  不能据 0.000s 判断它免费。

多副本租约的设计结论见 [2026-11-04-lease-design.md](2026-11-04-lease-design.md)（DB 抢占，不实现）。

### 三处断点实测收益（before/after，2026-11-04 实测）

命令：`uv run python <temp>/breakpoint_gain.py`（离线探针，零网络）。每个场景：
干净跑 → 在最坏窗口强杀（阶段完成、检查点未落盘；citation 为“文件已写、状态未落库”）
→ 续跑。每次 LLM/抓取注入 0.3s 延迟，使重复调用可计时。旧行为通过
`LIFECYCLE_ATOMIC_REPORT=0` / `LIFECYCLE_REPORT_DRAFT=0` / `LIFECYCLE_PAGE_CACHE=0` 原样复现。

| 断点 | 变体 | 重跑阶段耗时 | 外部抓取次数 | 阶段 LLM 次数 | 产物/台账 |
|---|---|---|---|---|---|
| citation 幂等写 | 旧 | 0.003s | 0 | 0 | **2 个报告文件 / 1 行台账** |
| citation 幂等写 | 新 | 0.004s | 0 | 0 | **1 个报告文件 / 1 行台账** |
| report 草稿 | 旧 | 0.610s | 0 | **2** | 1 文件 / 1 行 |
| report 草稿 | 新 | **0.312s** | 0 | **1** | 1 文件 / 1 行 |
| crawl 页缓存 | 旧 | 1.647s | **1 次完整抓取** | 1（抽取） | 1 文件 / 1 行 |
| crawl 页缓存 | 新 | **1.322s** | **0 次** | 1（抽取） | 1 文件 / 1 行 |

结论：

- report 草稿把重跑的 2 次 LLM 降为 1（矩阵推导仍重跑，报告生成复用草稿），
  省下的 0.298s ≈ 注入的 0.3s；生产按真实报告单位耗时同比例放大。
- crawl 页缓存把重跑的外部抓取从 1 次降为 0，省下的 0.325s ≈ 注入的 0.3s；
  LLM 抽取仍会重跑 1 次（缓存只省网络，不省抽取），这是刻意保留的正确性边界。
- citation 幂等写不省时间，但把“文件已写、状态未落库”窗口的重复产物从 2 降到 1，
  续跑后磁盘文件数 = 台账行数。

## 未实测 / 已知边界

1. **鉴权站点续跑**：凭据不落盘（既有安全边界），崩溃后恢复会丢失登录态，相关站点会失败。这是刻意取舍，不做绕过。
2. **多副本并发恢复**：单实例 10+ 任务已实测；同一 SQLite 多副本/多 worker 同时开机仍会重复恢复——当前无分布式租约（设计结论见 [2026-11-04-lease-design.md](2026-11-04-lease-design.md)，未实现），ADR 已把"多副本必须关闭"列为硬性前置。
3. **多地评测前后对照**：改造前未跑同一 25 case；用 v1.8 基线可比项对照。

## 开关与回滚

| 开关 | 默认 | 作用 |
|---|---|---|
| `LIFECYCLE_STAGE_EVENTS` | 1 | 阶段 start/end 事件 |
| `LIFECYCLE_CHECKPOINTS` | 1 | 阶段检查点落 SQLite |
| `LIFECYCLE_CANCEL` | 1 | 取消信号检查 |
| `LIFECYCLE_ATOMIC_REPORT` | 1 | 报告按 task 固定文件名 + 原子替换（0=旧时间戳命名、可能重复） |
| `LIFECYCLE_REPORT_DRAFT` | 1 | 报告草稿按 task 落库，重跑复用（0=每次重新生成） |
| `LIFECYCLE_PAGE_CACHE` | 1 | 无凭据站点页快照按 task 落库，重跑复用（0=整段重抓） |
| `CACHE_PRUNE_ENABLED` | 1 | 启动钩子清理开关（0=冻结启动清理；CLI 显式 `--apply` 不受此开关影响） |
| `CACHE_PRUNE_ON_STARTUP` | 0 | 启动时执行一次真实清理（默认关，避免每次重启写库） |
| `CACHE_COMPLETED_KEEP_DAYS` | 7 | completed/cancelled/partial 终态缓存保留天数 |
| `CACHE_FAILED_KEEP_DAYS` | 30 | failed 保留天数（复盘窗口更长） |
| `CACHE_MAX_ROWS` | 300000 | page_cache + task_drafts 全局行数上界 |
| `CACHE_MAX_BYTES` | 2147483648 | 全局数据字节上界（2 GiB，不含 SQLite 页开销） |
| `LIFECYCLE_RECOVER_ON_STARTUP` | 0 | 进程启动自动恢复 running 任务（生产单实例显式置 1，见 ADR） |
| `LIFECYCLE_RECOVER_CONCURRENCY` | 2 | 自动恢复同时执行的任务数上限 |
| `UNIT_FETCH_TIMEOUT` | 240 | 单站抓取超时（秒） |
| `AGENT_CONTEXT_FOLD_TOKENS` | 24000 | 历史 token 超过该值触发折叠；低于该值的预算不注册 `read_evidence` |
| `AGENT_CONTEXT_FOLD_KEEP_RECENT` | 4 | 折叠时保留的最近消息条数 |
| `AGENT_CONTEXT_FOLD_MIN_CHARS` | 200 | 小于该长度的 tool 观察不折叠 |
| `AGENT_UNREAD_EVIDENCE_WARN_THRESHOLD` | 1 | 折叠未回读且被终答引用的证据达到该值时告警；0 只计数 |

回滚任意一步：把对应开关置 0 即可停用行为；契约字段为加法，删除新文件不影响旧调用。

`CACHE_PRUNE_ENABLED` 的实际作用域只有启动钩子：置 `0` 不会阻止 `python -m src.storage.prune --apply` 删数据。
