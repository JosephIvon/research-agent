# ADR-001：进程启动自动恢复 running 任务的默认值

- 状态：已接受（2026-11-04）
- 决策者：research-agent 维护者
- 相关：`server.py::_recover_running_tasks`、`src/storage/database.py` 的 `tasks`/`task_events`/`task_checkpoints`、[2026-11-04-track.md](2026-11-04-track.md)

## 背景

P2 之后，任务在每个阶段成功后把检查点写入 SQLite（`task_checkpoints`，append-only），
并把 `tasks.status` 置为 `running` 直到终态。进程被强杀时，SQLite 里会留下若干
`running` 行——它们是"上次没跑完"的唯一跨进程证据。

目前由 `LIFECYCLE_RECOVER_ON_STARTUP`（默认 `0`）控制系统启动时是否自动把这些
任务从最近检查点续跑。只留一个布尔变量让部署方自己猜，会带来两种错误默认：

- 默认开：多副本/多 worker 部署会**互相抢跑同一批任务**（当前没有分布式租约），
  造成重复抓取、重复计费、重复写报告；
- 默认关：单实例生产崩溃后任务永远停在 `running`，需要人工调用 `/resume`。

本 ADR 给出确定默认值、前置条件、代价与必须关闭的清单。

## 决策

**代码默认值保持关闭（`LIFECYCLE_RECOVER_ON_STARTUP=0`）。
生产单实例部署的标准启动配置必须显式置 `1`，并作为部署清单项验收。**

这不是"看情况"：默认值面向最广的部署形态（开发/测试/多副本共享库），
错误默认的代价是不对称的——重复执行的代价（重复抓取被封、重复写产物、
重复计费）远高于"崩溃后需要人工 resume 一次"。因此把安全的一侧作为默认，
把"要恢复"作为部署方的显式选择。

推荐的成对默认值（生产单实例）：

```
LIFECYCLE_RECOVER_ON_STARTUP=1
LIFECYCLE_RECOVER_CONCURRENCY=2      # 同时只跑 2 个恢复任务
```

## 前置条件（不满足就不要开）

1. **单实例，或唯一的恢复者**：同一 SQLite（同一 `DATABASE_PATH`）只能有一个进程
   执行启动恢复。`uvicorn --workers N`（N>1）、K8s 多副本、滚动发布的重叠窗口
   都不满足。多副本要开恢复，必须先有分布式租约/leader 选举——当前刻意没做。
2. **TaskStore 与 SQLite 可达**：`TASK_STORE_BACKEND=redis` 时 Redis 必须已连接
   （恢复要把任务句柄重新装回 store）；SQLite 文件必须可写，且与崩溃前是同一份。
3. **输出目录一致**：`output/` 与崩溃前同一路径，否则续跑会写丢产物或重复写。
4. **下游配额已对齐**：`LIFECYCLE_RECOVER_CONCURRENCY` ≤ 目标站点/LLM 供应商
   能承受的并发；默认 2 是保守值。
5. **运维可观测**：至少保留 `task_events` 与 `app.log`。恢复失败会写
   `error` 事件（含 `reason_code`）并落 `failed` 终态，日志带 `task_id`。

启动预热不需要额外的"先空跑一轮"：恢复钩子在应用开始接流量前扫描 SQLite 并
按上限调度；LLM/配置在导入期已加载。若依赖远端 Redis，等待其就绪属于第 2 条。

## 打开后的代价

1. **重启风暴**：N 个 `running` 任务会在一次启动时全部被调度。已用
   `LIFECYCLE_RECOVER_CONCURRENCY`（默认 2）限流，峰值并发可在日志
   `启动恢复并发槽获取 ... active=N limit=M` 中核对。
2. **重复抓取 / 重复计费**：检查点只在阶段成功后落盘，恢复从**该阶段的下一段**
   开始；但如果崩溃发生在阶段中间，该阶段会重跑（例如抓到一半的 crawl 重抓）。
   对限流站点这会把恢复变成二次限流压力；对按 token 计费的 LLM 会二次计费。
3. **凭据类站点必然失败**：凭据不落盘（既有安全边界），恢复后登录态丢失，
   需要登录的站点会失败。这是既定取舍，不通过放松安全边界解决。
4. **坏行会被判失败**：没有任何检查点、或检查点缺重建字段的残留行，启动时直接
   标 `failed` 并写 `reason_code`（`no_checkpoint` / `request_rebuild_failed`）。
   这是期望行为——它们本就没有可恢复的证据。
5. **一次恢复失败不会无限重放**：恢复过程中的异常会落 `failed` 终态 + `error`
   事件，下一轮重启不会再被当作 `running` 反复拉起。

## 什么情况下必须关（`LIFECYCLE_RECOVER_ON_STARTUP=0`）

- 同一数据库存在**多于一个**应用进程（多 worker、多副本、滚动发布的旧新并行）。
- 开发/测试环境，尤其 FastAPI `TestClient` 启动——否则会无条件触发真实网络抓取。
- 数据库刚从备份恢复/迁移完成，其中大量 `running` 是历史脏数据，不是本次崩溃残留。
- 任务由外部调度器（cron、队列、工作流引擎）负责重投；自动恢复会和外部重投叠加。
- 目标站点处于限流/封禁风控期，任何额外请求都会扩大封禁面。
- 绝大多数任务依赖登录态、而崩溃后无法重建会话——自动恢复只会制造一串失败。
- 正在做"冻结现场"的故障复盘：需要保留崩溃时 SQLite 原样，不能被恢复改写。

## 后果

- 正向：单实例生产重启不再需要人工 `/resume`；恢复行为、并发上限与失败原因都可审计。
- 负向：多副本场景必须显式关闭；恢复阶段会重跑未完成阶段（成本与请求可观测但不为零）。
- 回滚：置 `LIFECYCLE_RECOVER_ON_STARTUP=0` 即停用；事件/检查点表与手动 `/resume` 不受影响。
