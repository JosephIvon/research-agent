# 交付级整改的验收基线（4 家竞品）

> 这份基线来自用户对公开资料的交叉核对，**未经本仓库独立核实**。
> 它的用途是给"下一次真实跑"提供逐条对照口径，不是当成仓库的既有事实。

## 背景

2026-10-27 用户实跑（`--urls` 指定站点 + `--no-search`）4 家真实竞品，结论是
"能用但不能直接交付"：

| 环节 | 实测 |
|---|---|
| 抓取 | 4/4 成功（含 JS 渲染页） |
| 信息提取 | 2 次 `Empty response`（JSON 解析失败） |
| 报告生成 | `APITimeoutError`（120s）→ 重试后 `status=failed` |
| 报告内容 | 框架、对比表、`[e:id]` 引用都在，但晓餐/川为大量"无法确认" |
| 竞品命名 | 域名当名字：`Chuanweidp / Meicai / 123 / Cloud`，腾讯云文章被当成"晓餐" |
| 自评分 | 明明 `failed`、两家没数据，仍打"可信度 10/10、质量 10/10（A 级）" |

整改分三条提交：

- `c6bb91f` fix(delivery)：抽取独占 token 预算与重试、兜底失败标记、失败作废分数、
  评分按"有数据竞品占比"打折、竞品命名（品牌名 → 站点 `<title>` → 已知站点 → 域名）、
  LLM 读超时 120s → 300s、CLI 标签改回"来源覆盖率"。
- `0337b66` fix(report)：报告生成改流式——非流式下读超时是**硬上限**
  （实测：超时 8s 时 openai SDK 连打 3 次、每次 8s，最终 25.9s 才抛错；
  超时 120s 就是 120s×3 ≈ 6 分钟，然后 `status=failed`）；
  流式下超时只约束"两个 chunk 的间隔"，整段生成可以远超它。
- 第三条提交（`fix(comparison)`）：**对比分析器只按中文关键词匹配维度，而抽取提示词发给模型的标准 key
  是英文**（pricing/features/models/target_users…）——两边对不上，对比表整列"未知"、
  完整性"0 个维度有数据"，报告正文只能写"无法确认"。这条才是"大量无法确认"的直接原因。

## 真实 provider 实测（2026-10-27，MiniMax-M3.1-Flash）

| 环节 | 实测 |
|---|---|
| 抽取（8192 预算） | 9.0s，5 条结构化数据，key = `name/pricing/models/features/source`，**未走兜底** |
| 报告生成（流式） | 54.4s / 82.2s / 194.4s 三次，**在 30s 读超时下全部成功**（总时长远超超时） |
| 报告生成（非流式） | 同一 30s 超时：3 次尝试全部 `httpx.TimeoutException`，**92.2s 后抛 `LLMError`**；超时 8s 时 25.9s 就抛 |
| 报告内容 | 4 家真名齐全、事实逐条带 `[e:xxxx]`、无"未获证/无法确认"，并主动标注"未公开披露" |
| 推理块 | 三次报告正文均无 `<think>`（客户端边界剥离生效） |

同参数对照（都是 30s 读超时）：**流式 54.4s 成功，非流式 92.2s 失败**。
openai SDK 默认 `max_retries=2` → 每次超时都重打一遍，所以非流式是
"超时 × 3 次"才报错：旧的 120s 默认值 ≈ 6 分钟后 `status=failed`（用户实测吻合）。
**读超时约束的是"有没有数据到达"，不是"生成要多久"**——流式下到达的是 chunk，间隔远小于超时。

## 期望结论（对照用）

| 竞品 | 交叉核对到的关键事实 |
|---|---|
| 晓餐 | 广佛区域；月成交约 6000 店；年 GMV 约 2 亿；只有两个小程序；地推不代下单——"重系统、轻人力" |
| 川为 | 9 大仓；单仓 6000+ SKU；覆盖 150+ 城市；58 万商户；一包起送 + 次日达；自研 App/小程序 |
| 美菜 | 2019 年 74 仓、1.7 万辆车；2021 年收缩转平台——重资产不是护城河，密度和履约质量才是 |
| 快驴 | 22 省 45 城；百万商户；全品类；不支持月结——赊销/账期是差异化钩子 |

逐条核对口径：

1. **竞品名必须是真名**，不允许再出现 `Chuanweidp / Meicai / 123 / Cloud`。
2. 报告里每家的关键数字要么带 `[e:xxxx]` 证据标记，要么明确写"未公开披露"；
   不允许用"无法确认"敷衍，也不允许留无源断言。
3. 4 家里 2 家拿不到数据时，任务不得显示 10/10 或 A 级；任务 `failed` 时不得显示任何质量分。
4. CLI 上那个数就叫"来源覆盖率"，不要再叫它"可信度"——它从来不是可信度。

## 已知未修的限制（会直接影响第 2 条）

**页级来源粒度不够**：抓取会把站内多个页面的正文拼成一段交给模型
（`web_crawler.combine_page_texts` 给每页加 `### Source URL:` 前缀），
但抽取出的每一条数据只挂**入口页 URL**（`mvp_workflow.py` 里 `source_url = url`）。

后果：事实其实来自站内某篇报道文章时，`[e:xxxx]` 指向的却是首页——读者点进去找不到那句数字；
更糟的情形就是"把第三方文章当成竞品官方说明"（用户实测里腾讯云文章被当成了晓餐）。

尚未实现的修法方向：抽取后按 value 文本回查命中页，把 `source_url` 换成真正含该事实的那一页；
回查不到就退回报入口页并标注"页级归属未确认"，不允许继续假装是页级精确。

另两条已知未修：

- **前后端等级阈值分叉**：后端 8.0/6.0/4.0/2.0（`quality_scorer.py`），前端 8.5/7/5.5/3
  （`frontend/src/utils/reportGrade.js`，注释却写"与后端保持一致"），且前端优先用数值分重算等级——
  后端给 A 的报告，前端可能显示成 B。
- **空报告平凡通过**：`verify_report("")` → `passed=True`、四个指标全 1.0
  （`agent/citations.py`）。失败路径不经过它，所以本轮没动；既有测试有意钉住这个语义。

还有一条**结构性的**：维度标准 key 现在写在三处——抽取提示词（`mvp_workflow.py` 的
"请优先使用以下标准 key"）、`quality_scorer.DIMENSIONS`、`comparison_tool` 的关键词表。
本轮修的正是第三处与第一处对不上导致的"对比表全空"；三处没有单一权威来源，
下次再加维度还会漂。收口方向：抽一个共享的维度常量，提示词、评分器、对比分析器都从它生成。

## 复跑后看三处

```bash
python main.py --urls "<4 个站点>" --no-search
```

1. **竞品抓取** 那几行里的名字是不是真名（`main.py` 逐家打印 `name`）。
2. **数据质量** 那行：4 家里 2 家没数据时，它必须不再是 10.0/A；任务失败时这行不该出现。
3. **报告预览**：对照上面那张表逐条看，缺的那条是"没抓到"还是"抽到了没写进报告"；
   对比表里每一格都该是事实或"未知"，**不该整列是"未知"或"未获证"**——那是对比分析器
   没读到数据的信号。
