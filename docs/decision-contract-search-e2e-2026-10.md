# 决策契约：真实搜索引擎端到端（2026-10-28）

> 纪律：**判定线必须在看到数据之前写死**。看到数据后再定阈值等于给结论找理由。
> 本文件在实跑之前定稿，实跑结果另存 `output/search_e2e_*.md`，结论以本文件为准。

## 0. 为什么现在跑

上一轮把"澄清与定界层 + 搜索四段式"接进管线，但**只在替身搜索引擎下验证过**。
真链路没跑，等于"搜索质量"这件事至今没有实测依据。

更要紧的是，早前实测到过一个具体缺陷：任务句式查询（"找一下百度搭子的全部竞品信息"）
下，最该抓的**官方介绍页**与**竞品盘点页**会被相关性过滤丢掉，而媒体/百科页会被当成竞品。
新管线（先澄清 → 再按计划发短查询词）就是为修这个而做的，**但必须用真搜索引擎验证它真的修好了**。

## 1. 这次要回答的问题（Q1–Q5）与判定线

| 编号 | 问题 | 判定线（预先写死） | 不达标时的默认动作 |
|---|---|---|---|
| Q1 | 计划层能否把"百度搭子"认成具体主体 | 主体名非空 **且** `resolved_confidence ≥ 0.5` | 记为"计划层在真实模型上不可靠"；搜索按默认计划查询词跑（现有降级路径），并把"主体消歧"列为待修项 |
| Q2 | 发现质量：候选池里有多少是竞品官网 | 候选池 ≥ 5 家 **且** 入选名单中"非媒体/百科域"占比 ≥ 80%（样本 = 该组入选名单；入选 0 条的组按 0% 判） | 扩充站点类型过滤表（应用商店、导航站、电商、比价站等）；不改阈值 |
| Q3 | 任务句 vs 搜索词：管线是否对句式不敏感 | 同一主体两种句式的**入选名单 Jaccard ≥ 0.5** | 查询规划没起作用：把主体名与意图词直接拼进 entity_anchor / competitor_discovery 查询 |
| Q4 | 入选正确性：入选的是不是同一赛道 | 人工核对 ≥ 3/4 属于主体所在赛道 | 准入口径（"什么算竞品"）需要更硬的约束，或必须允许用户给竞品名单 |
| Q5 | 反证段有没有产出 | 至少 1 条 counter_evidence 结果（带 URL） | 反证查询词换法（"差评/投诉"→ 站点限定 + 产品名），或降级为"反证仅靠站内评价页" |

**不达标 ≠ 失败**：不达标时执行"默认动作"那一列，并如实记录。禁止事后调阈值。

## 2. 样本、口径与成本

- **主体 2 个**：百度搭子（用户举的例子，AI 搭子/AI 陪伴赛道）、猫箱（已知同赛道产品，做交叉对照）。
- **句式 2 种**：
  - task 句式：`找一下百度搭子的全部竞品信息`（长句、含动作词与修饰词）
  - search 句式：`百度搭子 竞品`（短搜索词）
- **共 4 组**（2 主体 × 2 句式）。不重复跑同一组取平均：搜索结果本身有抖动，
  交叉设计（2 主体 × 2 句式）比单组重复更能分辨"系统性差异"与"单次抖动"。
- **每组做**：1 次计划 LLM 调用 + 四段式搜索（entity_anchor / competitor_discovery /
  per_competitor_verify / counter_evidence，各阶段查询 ≤ 4 条）。
- **默认不整站抓取**：Q1–Q5 全部可在"搜索 + 入选"层判定，抓取只会把墙钟拉长。
  抓取链路单独跑 1 组（`--with-crawl`）做端到端确认。
- **记录字段**（每组）：计划实体与置信度与备选、每阶段查询词与结果数与去重后 URL 数、
  候选池逐条（名称/URL/是否媒体站/被打分理由）、入选逐条（分数与理由）、剔除清单、
  counter_evidence 结果条数与标题。

## 3. 已知干扰与口径边界

1. **搜索引擎结果抖动**：同一 query 两次结果不同。结论只在 4 组交叉后成立，不做单点断言。
2. **媒体站判定是启发式**（域名片段 + 路径片段），不是人工标注；Q2 的"非媒体域占比"
   以本仓库同一套判定为准，与管线行为一致（否则测的是另一套标准）。
3. **SearXNG 在本机 8888**（`.env` 的 `SEARXNG_URL`），`language=zh-CN`、`categories=general`。
   换后端（Bing/SerpAPI）结论可能不同，本轮不覆盖。
4. **计划由真实模型产出**：本轮用的就是生产默认 provider。若某组计划被拒（结构不合格），
   记为"该组走默认计划"，仍参与 Q3（默认计划也有查询词），但在 Q1 判定里单独标注。

## 4. 实跑之后要交付的东西

1. `output/search_e2e_<ts>.md`：逐组明细 + 五个问题的 PASS/FAIL 判定。
2. `output/search_e2e_<ts>.json`：原始记录（供复算）。
3. `output/search_e2e_<ts>.review.json` + `.review.md`：**人工核对表**（Q2 的判定依据）。
4. 本文件追加"实测结论"一节：每个问题的事实、判定、以及不达标项的处置。
5. 若有代码缺陷 → 修 + 补回归测试（不靠改判定线让结论变好看）。

| Q1 / Q5 | 不变 | — | — | 不变 |

**Q2 的执行方式变了**：工装不再自己给 Q2 下结论。

- 实跑产出 `output/search_e2e_<ts>.review.json`（逐条待核对）与 `.review.md`（人读版）。
- 人工把每条的 `verdict` 填成 `true`（是该主体的真竞品官网）/ `false`；
- 填完跑 `uv run python tool_e2e_search_real.py --judge-review <路径>`，按线判 Q2（不联网）。
- 没填完 → Q2 记「⏳ 待人工核对」，**不写 PASS 也不写 FAIL**。
  代理判定（同仓库的站点类型表）打出来的分数只作为人工核对的参考列，
  不作为判定依据——它是被测对象。

**已知的判据局限（写下来，别装作没有）**：Q4 的"产品官网"这一层用的是
同一套代码判出来的站点类型，所以 Q4 仍然**部分自证**；Q2 的人工核对是唯一的外部证据。
Q4 与 Q2 都过，才算发现质量站得住。

## 2. 五个问题的结论

| 编号 | 结论 | 依据 |
|---|---|---|
| Q1 主体消歧 | ✅ PASS | 每轮 4/4 组都解析出主体且置信度 0.55–0.93；模型给的 `what_it_is` 与备选都可用；模型还认出了「百度搭子（DuMate）」这个别名 |
| Q2 发现质量 | ⚠️ 线按"非媒体域占比"判，**这条线自证无效** | 见 §4 |
| Q3 句式不敏感 | ❌ FAIL（基线 Jaccard 0.00 / 0.18，线是 0.5）—— **2026-10-29 已查清真正原因：这条线现在测不到它想测的东西** | 召回测量实测：**同一句式重复跑**，入选名单两两 Jaccard 只有 **0.042–0.235**（两组是 0.0）。再往上游查，**同一主体两次生成的调研计划，查询词 Jaccard 只有 0.097（猫箱）/ 0.125（百度搭子），10 对计划无一对逐字相同**——计划查询词每次都换 → 搜到的结果集换 → 候选池换 → 入选名单当然不重合。**Q3 的跨句式 Jaccard 在这种抖动下不可能达标**（阈值是实跑前定稿的，**不改**）。见 `docs/discovery-recall-measurement.md` §7.5–7.6 |
| Q4 入选正确性 | ⚠️ 代理判据太松，人工核对才是绑定结论 | 见 §3。**补（2026-10-29）**：召回测量显示假阳性出在"同赛道"这一层，不在"是不是官网"这一层——`talkie.ai`（医疗）、`hoshinoresorts.com`（酒店）、加密钱包站都有独立域名且路径是首页，站点类型判定看不出问题 |
| Q5 反证段 | 基线 1/4 组为 0；修后各轮在有入选的组里都能出结果 | 候选名干净之后反证查询才有效（候选名是文章标题时，搜出的是 KPMG 白皮书） |

## 4. 判定线本身的问题（要说清楚，不能装作没有）

- **Q2 是自证的**：它用"本仓库同一套非媒体域判定"来判定候选池质量，而那套判定
  正是被测对象。基线按这条线是 PASS，人工核对是 19%。**这条线测不出该测的东西**。
  改法（下一轮）：Q2 改成"人工核对入选项里真竞品官网的占比"，并把人工核对写进工装
  （现在的 `tool_e2e_search_real.py` 只做代理判定，人工部分在这一节手工完成）。
- **Q4 的代理判据太松**：它按标题/摘要里有没有"AI/陪伴/角色"这类词判同赛道，
  于是"15个AI虚拟女友/男友社交软件，专属恋爱聊天和情感陪伴"（一篇文章）也算同赛道。
  改法：Q4 的代理判据要加"必须是产品官网"这一层。
- **Q3 的 FAIL 有真实原因**：基线两种句式的入选名单几乎不重叠。
  原因不是"任务句式处理不了"，而是**两边都在选垃圾**——两边的错法不同，所以交集是空。
  修完站点类型判定后这一项要重新测才有意义。

## 5. 没做到的事（不粉饰）

- 抓取阶段仍会撞上真实世界的脏东西（PDF 触发 "Download is starting"、
  apps.apple.com 连接被断、talkie.ai 首页 60 秒超时、页面注入嫌疑被整页丢弃）。
  这些都**有兜底**，但没有为"抓取失败"设计"换一家补位"的机制
  （见 `docs/admission-metric-gap.md` 的 (b)）。
- 搜索引擎结果本身抖动明显：同一 query 两次结果不同，`猫箱 竞品` 这一组在
  修后第一轮里只搜到媒体页 → 候选池 0 → 入选 0。**空结果是可能发生的**，
  这直接决定了入选指标不能只靠"搜索结果长什么样"。
- **最后一组（猫箱/search）本轮仍归零**：模型没提名竞品、搜索式查询也没搜到官网。
  这条链路目前是"尽力而为"，没有保底。
- 词面判断仍然会错：修后第四轮里"星野集团"（一家酒店公司，hoshinoresorts.com）
  被当成"星野 AI"的竞品——第五轮已用"标题完全一致优先"修掉，
  但**跨行业的同名公司**要根治还得靠语义判断（模型或人）。

  抓到 0 个候选 → 抓取目标为空 → 后续流程报错。**"没有竞品"这条路径没有走通到底**，
  需要单独处理（是空结果交付、还是提示用户补竞品名）。

## 3. Q3 的 FAIL 与上一轮**不是同一个病**（重要区别）

上一轮 Q3 FAIL 的原因是"两边都在选垃圾"，交集自然为空。
这一轮两边选出的**都是真竞品官网**（人工核对 5/5 与 7/8），但**没有一家重合**：

| 主体 | task 句式选中 | search 句式选中 |

| 百度搭子 | CHAI | Tofai、夜色AI、星野、独响 |

所以 Q3 现在测的不是"句式处理能力"，而是**发现阶段的召回本身**：
从同一个赛道里，两次不同的查询捞回来的官网重合度接近 0——

这不是本轮该修的缺陷，但它把 Q3 这条线的**性质**暴露了出来：
它测的是"两种句式的检索结果是否稳定收敛到同一批官网"，
需要**更大的候选池 + 更稳定的排序**才可能达到 0.5。
**本轮不动这条线**（阈值与语义都没动），把观察如实记在这里。

## 4. 这一轮抓到的第三个代码缺陷：搜索后端失败被当成"没找到竞品"

第六轮第一次实跑时，有 3 组直接归零（候选 0、入选 0）。查出来不是"这个赛道没竞品"：

- SearXNG 的引擎会**集体超时或被限流**（`unresponsive_engines: ["duckduckgo timeout",
  "google cse Suspended: too many requests"]`），此时整轮返回 **0 条**；
- 旧代码把 0 当成"没搜到" → 候选池归零 → 整组结论作废，还看不出原因。

修法：`SearchTool` 抛可区分的 `SearchBackendError`（空结果 **且** 引擎集体无响应才抛，
重试一次仍如此）→ 阶段层记 `search_failed` → 工装把这类组**重跑**。
第七轮实跑 4 组均未触发重试（后端正常）。

## 2. 一个必须说清楚的事实：**端到端数字被搜索抖动主导，不能用来比较两轮**

| 组 | 候选池（第六轮 → 第七轮） | 入选（第六轮 → 第七轮） |
|---|---|---|
| 百度搭子/task | 55 → **13** | 6 → **0** |
| 百度搭子/search | 39 → **14** | 5 → 2 |
| 猫箱/task | 15 → **32** | 8 → 5 |
| 猫箱/search | 11 → **7** | 1 → 1 |

同一个主体、同样的句式，候选池能从 55 掉到 13——**搜索结果本身变了大半**，
模型这一轮给的计划与查询词也不同。所以：

- **第六轮与第七轮的数字不能互相比较**（改的不只是判定，还有搜索结果与计划）；
- 本轮修的缺陷（下载站子域、百科页、门户详情页）的效果，
  **由确定性回归测试证明**（拿人工核对抓到的原样 URL 做断言），
  而不是由这两轮的占比变化证明——那会把搜索抖动算到修复头上。

**这是本轮实测最重要的方法论结论**：这套系统的端到端发现质量，
在同一份代码上波动幅度大到可以淹没修复效果。
单轮数字只能当"这一刻的观察"，不能当"这个版本的性质"。
