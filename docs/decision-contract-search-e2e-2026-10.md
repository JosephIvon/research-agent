# 决策契约：真实搜索引擎端到端（2026-10-28）

> 纪律：**判定线必须在看到数据之前写死**。看到数据后再定阈值等于给结论找理由。
> 本文件在实跑之前定稿，实跑结果另存 `output/search_e2e_*.md`，结论以本文件为准。

## 0. 为什么现在跑

上一轮把"澄清与定界层 + 搜索四段式"接进管线，但**只在替身搜索引擎下验证过**。
真链路没跑，等于"搜索质量"这件事至今没有实测依据。

更要紧的是，早前实测到过一个具体缺陷：任务句式查询（"找一下百度搭子的全部竞品信息"）
下，最该抓的**官方介绍页**与**竞品盘点页**会被相关性过滤丢掉，而媒体/百科页会被当成竞品。
新管线（先澄清 → 再按计划发短查询词）就是为修这个而做的，**但必须用真搜索引擎验证它真的修好了**。

## 1. 这次要回答的问题（Q1–Q5）与判定线

| 编号 | 问题 | 判定线（预先写死） | 不达标时的默认动作 |
|---|---|---|---|
| Q1 | 计划层能否把"百度搭子"认成具体主体 | 主体名非空 **且** `resolved_confidence ≥ 0.5` | 记为"计划层在真实模型上不可靠"；搜索按默认计划查询词跑（现有降级路径），并把"主体消歧"列为待修项 |
| Q2 | 发现质量：候选池里有多少是竞品官网 | 候选池 ≥ 5 家 **且** 入选名单中"非媒体/百科域"占比 ≥ 80% | 扩充站点类型过滤表（应用商店、导航站、电商、比价站等）；不改阈值 |
| Q3 | 任务句 vs 搜索词：管线是否对句式不敏感 | 同一主体两种句式的**入选名单 Jaccard ≥ 0.5** | 查询规划没起作用：把主体名与意图词直接拼进 entity_anchor / competitor_discovery 查询 |
| Q4 | 入选正确性：入选的是不是同一赛道 | 人工核对 ≥ 3/4 属于主体所在赛道 | 准入口径（"什么算竞品"）需要更硬的约束，或必须允许用户给竞品名单 |
| Q5 | 反证段有没有产出 | 至少 1 条 counter_evidence 结果（带 URL） | 反证查询词换法（"差评/投诉"→ 站点限定 + 产品名），或降级为"反证仅靠站内评价页" |

**不达标 ≠ 失败**：不达标时执行"默认动作"那一列，并如实记录。禁止事后调阈值。

## 2. 样本、口径与成本

- **主体 2 个**：百度搭子（用户举的例子，AI 搭子/AI 陪伴赛道）、猫箱（已知同赛道产品，做交叉对照）。
- **句式 2 种**：
  - task 句式：`找一下百度搭子的全部竞品信息`（长句、含动作词与修饰词）
  - search 句式：`百度搭子 竞品`（短搜索词）
- **共 4 组**（2 主体 × 2 句式）。不重复跑同一组取平均：搜索结果本身有抖动，
  交叉设计（2 主体 × 2 句式）比单组重复更能分辨"系统性差异"与"单次抖动"。
- **每组做**：1 次计划 LLM 调用 + 四段式搜索（entity_anchor / competitor_discovery /
  per_competitor_verify / counter_evidence，各阶段查询 ≤ 4 条）。
- **默认不整站抓取**：Q1–Q5 全部可在"搜索 + 入选"层判定，抓取只会把墙钟拉长。
  抓取链路单独跑 1 组（`--with-crawl`）做端到端确认。
- **记录字段**（每组）：计划实体与置信度与备选、每阶段查询词与结果数与去重后 URL 数、
  候选池逐条（名称/URL/是否媒体站/被打分理由）、入选逐条（分数与理由）、剔除清单、
  counter_evidence 结果条数与标题。

## 3. 已知干扰与口径边界

1. **搜索引擎结果抖动**：同一 query 两次结果不同。结论只在 4 组交叉后成立，不做单点断言。
2. **媒体站判定是启发式**（域名片段 + 路径片段），不是人工标注；Q2 的"非媒体域占比"
   以本仓库同一套判定为准，与管线行为一致（否则测的是另一套标准）。
3. **SearXNG 在本机 8888**（`.env` 的 `SEARXNG_URL`），`language=zh-CN`、`categories=general`。
   换后端（Bing/SerpAPI）结论可能不同，本轮不覆盖。
4. **计划由真实模型产出**：本轮用的就是生产默认 provider。若某组计划被拒（结构不合格），
   记为"该组走默认计划"，仍参与 Q3（默认计划也有查询词），但在 Q1 判定里单独标注。

## 4. 实跑之后要交付的东西

1. `output/search_e2e_<ts>.md`：逐组明细 + 五个问题的 PASS/FAIL 判定。
2. `output/search_e2e_<ts>.json`：原始记录（供复算）。
3. 本文件追加"实测结论"一节：每个问题的事实、判定、以及不达标项的处置。
4. 若有代码缺陷 → 修 + 补回归测试（不靠改判定线让结论变好看）。

# 实测结论（2026-10-28）

> 判定线在上面，**没有改过**。下面按线给结论，并附上"线没测出来、但人看出来了"的部分
> ——后者同样要记，因为代理判定不是人工核对。

## 1. 三轮实跑的设置

| 轮次 | 代码版本 | 样本 | 耗时 |
|---|---|---|---|
| 基线（修前） | 站点类型判定之前 | 2 主体 × 2 句式 | 52 min（含一次整站抓取） |
| 修后第一轮 | 加站点类型分类 | 2 主体 × 2 句式 | 37 min |
| 修后第二轮（终版） | 再加阶段名折叠、文件直链、更多域名与文章词 | 2 主体 × 2 句式 | 见下 |

搜索后端：本机 SearXNG（`http://localhost:8888`，`language=zh-CN`、`categories=general`），
逐条探测正常（连发 8 条查询，20–30 条结果/条，4–5 秒/条，**不是限流**）。

## 2. 五个问题的结论

| 编号 | 结论 | 依据 |
|---|---|---|
| Q1 主体消歧 | ✅ PASS | 4/4 组都解析出主体且置信度 0.55–0.93；模型给的 `what_it_is` 与备选都可用 |
| Q2 发现质量 | ⚠️ 见下 | 线按"非媒体域占比"判，基线也 PASS——**这条线自证无效**（见 §4） |
| Q3 句式不敏感 | ❌ FAIL（基线） | 百度搭子 Jaccard = 0.00；猫箱 Jaccard = 0.18（线是 0.5） |
| Q4 入选正确性 | ⚠️ 线按代理判 PASS，**人工核对不通过** | 见 §3 的逐条核对 |
| Q5 反证段 | ❌ FAIL（基线 1/4 组为 0） | 猫箱/search 组反证 0 条；且基线的反证查询词被垃圾候选名污染（搜出 KPMG 白皮书） |

## 3. 人工核对（这才是绑定结论）

**基线（修前）4 组共 26 个"入选竞品"，人工逐条核对：只有 5 个是真竞品官网（19%）。**

| 组 | 入选 | 是真竞品官网的 |
|---|---|---|
| 百度搭子/task | DuMate（=主体自己 dumate.cn）、DuMate（百度搭子）（aitoollab.cn 收录目录）、百度搭子DuMate…（aitop100.cn 收录目录）、Best AI Companions（similarlabs 文章页）、Lov.app、PurrlyAI酒馆、Saylo AI、Tofai | 4/8（Lov.app、PurrlyAI、Saylo AI、Tofai） |
| 百度搭子/search | ai-bot.cn 文章、apps.apple.com ×2、ai.fly63.com 分类页、aigc.cn 收藏页 | **0/5** |
| 猫箱/task | woshipm ×2、aitntnews、36kr、iopn.library（PDF 封面页）、pdf.dfcfw（PDF）、36kr、leiphone 分类页 | **0/8** |
| 猫箱/search | hub.baai.ac.cn 文章、woshipm、aitntnews、36kr、AI 织梦 | 1/5 |

**结论：修前"自动搜索竞品"这条链路基本不可用**——它把文章、应用商店页面、
收录目录、PDF，甚至主体自己，都当成了竞品。这不是"质量不够"，是**交付的东西不是竞品**。

### 由此暴露的四个代码缺陷（都已修 + 回归测试）

1. **准入只看"有独立域名"** → 媒体站、应用商店、收录目录全部通过。
   修：`src/workflow/site_types.py` 按站点类型判定（产品官网/媒体/UGC 平台/
   应用商店/收录目录），域名与路径是硬事实，**标题特征兜底**（盘点/对比/哪个好/
   榜单/实测 = 文章页）；文件直链（.pdf/.apk…）不算网站。
2. **主体自己进了竞品名单** → 主体叫"百度搭子"，它的产品官网叫 dumate.cn，
   名字完全对不上。修：锚定阶段排第一的产品官网 = 主体自己的官网（按域名排），
   计划新增 `entity.official_domains` 让模型也能给。
3. **阶段名对不上 → 整轮空转且看不出来** → 模型写 `discovery`/`verify` 时，
   该阶段被丢弃 → 0 条查询 → 候选池 0 家；从外面看像"搜索正常、就是没竞品"。
   修：阶段名同义折叠 + **每个阶段必有查询词**（缺则用默认词补）。
4. **报告输出为空 → 整轮失败** → 13 家竞品时推理块把 16384 预算吃光，
   正文没开始写 → LLMError → 跑了 17 分钟的轮次全丢。修：空则把预算翻倍
   重试一次（上限 32768），还空才判失败。

## 4. 判定线本身的问题（要说清楚，不能装作没有）

- **Q2 是自证的**：它用"本仓库同一套非媒体域判定"来判定候选池质量，而那套判定
  正是被测对象。基线按这条线是 PASS，人工核对是 19%。**这条线测不出该测的东西**。
  改法（下一轮）：Q2 改成"人工核对入选项里真竞品官网的占比"，并把人工核对写进工装
  （现在的 `tool_e2e_search_real.py` 只做代理判定，人工部分在这一节手工完成）。
- **Q4 的代理判据太松**：它按标题/摘要里有没有"AI/陪伴/角色"这类词判同赛道，
  于是"15个AI虚拟女友/男友社交软件，专属恋爱聊天和情感陪伴"（一篇文章）也算同赛道。
  改法：Q4 的代理判据要加"必须是产品官网"这一层。
- **Q3 的 FAIL 有真实原因**：基线两种句式的入选名单几乎不重叠（百度搭子 Jaccard=0）。
  原因不是"任务句式处理不了"，而是**两边都在选垃圾**（task 侧选到主体自己，
  search 侧选到应用商店页面）——两边的错法不同，所以交集是空。修完站点类型判定后
  这一项要重新测才有意义。

## 5. 没做到的事（不粉饰）

- 抓取阶段仍会撞上真实世界的脏东西（PDF 触发 "Download is starting"、
  apps.apple.com 连接被断、页面注入嫌疑被整页丢弃）。这些都**有兜底**，
  但没有为"抓取失败"设计"换一家补位"的机制（见 `docs/admission-metric-gap.md` 的 (b)）。
- 搜索引擎结果本身抖动明显：同一 query 两次结果不同，`猫箱 竞品` 这一组在
  修后第一轮里只搜到媒体页 → 候选池 0 → 入选 0。**空结果是可能发生的**，
  这直接决定了入选指标不能只靠"搜索结果长什么样"。
- 端到端抓取那一组（百度搭子/task）修后仍然 `status=failed`：
  抓到 0 个候选 → 抓取目标为空 → 后续流程报错。**"没有竞品"这条路径没有走通到底**，
  需要单独处理（是空结果交付、还是提示用户补竞品名）。
